## 1. 什么叫做最佳

本文的「最佳」是一个确定的结果，不是一份产品清单里的主观偏好。

按这个顺序取舍：

1. 满足已经写下来的一致性、隔离和恢复目标。
2. 授权在应用内按对象完成；边缘产品只做纵深防御。
3. 发布、回滚、备份和恢复能按第 11–12 节演练。
4. 在 1–3 都成立时，运行时组件最少，账单可以按第 14 节估算。
5. 团队熟悉 React、Vue 或某种框架，只在前四条打平时起作用。

因此：能用静态页面满足需求时，加 SSR 不是更优；能用一个 D1 满足一致性时，按租户拆库不是更优；官方某页把 KV 列为会话的常见存法，也不能覆盖第 10 节对立即撤权的要求。

决策按下面六问顺序做。每一问只有一个默认答案。改默认必须命中该问列出的触发条件，并写进第 16 节。没有触发条件就用默认。后面的问题不推翻前面已经成立的选择。

1. **公开页面能否在发布时生成？** 深层 URL 需要被索引：Astro 静态生成，真实 404。页面是登录后工具、深层 URL 不要求索引：Vite SPA，显式开启深链回退。两者都不是：进入第 2 问。
2. **不能预渲染的原因是什么？** 只有数据要在请求时读取、HTML 壳可以静态：静态资源加 Hono `/api/`*，Worker 只优先处理 API 前缀。搜索或首次访问必须看到请求时生成的 HTML，并且按发布重建的延迟已经被业务拒绝：Astro SSR，能预渲染的路由继续预渲染。「团队习惯用某框架」不是原因。
3. **是否必须使用 Next.js？** 默认不使用。已有应用，或功能清单证明 Astro 路线做不到：新项目和能迁移的项目用 vinext，先运行 `npx vinext check` 并看兼容矩阵。vinext 仍是 Beta；这个风险不能接受，就不要选 Next.js。已经运行在 OpenNext 上且 vinext 有明确缺口：保留 OpenNext，用它的 Workers runtime `preview` 验收最终产物，不靠 `next dev`。实施日重读 Node.js middleware 的支持情况；1.0 核查时该路径不支持。
4. **数据用哪一种？** 按第 5 节的表逐项选择。每增加一个存储产品，写下一句：少了它，哪条已记录的需求会不成立。写不出来就不要加。
5. **异步要到哪一层？** 失败后让用户重试就能成立：在请求里做完。需要削峰、重试和投递：Queues。步骤要跨过分钟或天，并在失败后补偿：Workflows。同一份事件要交给多个互不相干的消费者，或需要按保留期重放：K2；Beta 期间的存储和保留上限见第 5.6 节，装不下就不要选。Queues 是任务，K2 是日志，两者不互相替代。
6. **是否已经存在必须保留的外部系统？** 没有 PostgreSQL/MySQL、商业 CMS、消费者 IdP、支付、外部邮件或外部备份：不引入。已有：走第 3 节例外。Hyperdrive 只在例外批准之后出现，它是外部数据库的连接池和查询缓存，不是 Cloudflare 托管的数据库。

出现下列情况时，本文的默认栈不再声称是最佳，必须写成例外或改用注明的产品线：

- 主用户在中国大陆网络，而目标产品不在已签约的 China Network 覆盖内。
- 关系数据超过单个 D1 的 10 GB 硬顶，且不能按第 6.4 节的固定分片切开；或必须使用 PostgreSQL/MySQL 才有的能力。
- 工作负载必须是容器镜像、长期驻留进程或任意入站 TCP 服务。容器镜像走 Cloudflare Containers，并单独核算，不包装成普通 Worker。
- 客户要在平台上运行他们自己的 Worker 代码。这是 Workers for Platforms，不是「再部署一个 Worker」。
- 合规要求供应商级别的独立副本。多账户 R2 仍共享 Cloudflare 这一层故障域。

只记六条也可以评审：能预渲染就预渲染；权威关系数据在 D1，文件在 R2，允许旧值的公开配置在 KV，单实体协调在 Durable Objects；跨产品副作用用 outbox 和幂等键；授权按对象做；预览不碰生产；代码回滚不恢复数据。

## 2. 按应用类型的默认方案

下表是第 1 节的展开。同一行里没有写出的产品，就是本类型的默认不引入。

| 类型                      | 默认方案                                                                                           | 改选的触发条件                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| *纯静态内容站：文档、营销、博客*       | Astro 静态生成到 Workers Static Assets。每个公开 URL 一个 HTML，真实 404。内容在 Git 中经 PR 发布                     | 需要服务端私密计算，或发布重建的延迟已被业务拒绝。`_headers` 超过 100 条，或静态重定向超过 2,000 条、动态重定向超过 100 条时，才加 Worker 处理这些规则 |
| 纯前端应用：交互工具，深层 URL 不要求索引 | Vite SPA 到 Workers Static Assets，`not_found_handling` 为 `single-page-application`。不写 Worker 脚本 | 某个公开 URL 的首屏必须被索引：该 URL 改由 Astro 输出真实 HTML，不把营销页放进 SPA。出现本团队拥有的数据：加上面「静态壳 + API」一行，前端形态不变     |
| 静态壳 + 少量动态              | Astro 或 Vite 的静态资源，加一个 Hono Worker。`run_worker_first` 只包含 `/api/*`。关系数据用一个 D1，文件用一个私有 R2       | 命中第 1 节第 2 问的 SSR 条件                                                                          |
| 请求时公开 HTML              | Astro SSR 与 Cloudflare adapter；能预渲染的路由保持预渲染。公开且与身份无关的响应才允许进入缓存                                 | 功能清单证明必须 Next.js：走第 1 节第 3 问                                                                  |
| 复杂 SaaS：多租户、账号、后台任务     | 第 6.4 节。一个 Worker、一个 D1、一个私有 R2，租户列放在每一行业务数据上                                                  | 命中第 6.4 节的分片、拆 Worker、客户域名或客户代码条件                                                             |
| 实时协作：房间、文档、库存分片         | 每个实体一个 Durable Object，SQLite 存储为权威状态；WebSocket 使用 Hibernation                                  | 只是单向通知、没有单实体协调：用 Queues，不建 Durable Object                                                     |
| 已有外部 SQL                | 批准例外后用 Hyperdrive。认证、账务和写后立即读使用关闭查询缓存的独立配置                                                     | 数据可以迁入 D1 且规模落在第 5 节以内：迁入，不保留外部库                                                              |
| 检索或生成                   | 有现成内容、要托管式检索：AI Search。必须自己控制切分和 embedding：Vectorize + Workers AI。调用外部模型并要统一记录：AI Gateway      | 没有检索或生成需求：不接入。数据区域不满足评审：不做                                                                    |

纯前端应用不包含本团队的用户数据和文件。登录、会话、上传一旦出现，就同时适用第 6.2 或第 6.4 节，浏览器仍然只通过 HTTPS 调用自己的 API，不能读取 bindings。

React 与 Vue 在本文打平，用团队已经在用的那一个。新内容站用 Astro，不用 SPA 去承载要被索引的页面。

## 3. 不可妥协约束与例外

1. **基础设施范围。** 业务运行、权威数据和文件默认放在 Cloudflare 原生服务上，浏览器只经 HTTPS 访问公开入口。原生路径可以是静态资源、D1、KV、R2、Durable Objects、Queues、Workflows、K2 和 Analytics Engine 的组合。域名注册、代码托管、构建依赖、用户设备和公共互联网仍然是外部依赖。
2. **正确性。** 按第 5 节选择产品。KV、缓存和 isolate 内存不能充当事务权威源。队列消费者按重复和乱序设计。D1、R2、队列和外部服务之间没有共同事务。
3. **数据隔离。** 每个站点，以及开发、预览、预发、生产，都有可审计的资源和权限边界。预览不使用生产读写绑定或生产密钥。生产数据未经批准不复制到测试环境。
4. **安全和隐私。** 认证、对象级授权、秘密管理、日志脱敏，以及可执行的删除和恢复，先于公开上线。CORS、WAF、Access、Turnstile 和前端判断都不完成业务授权。
5. **运维。** 配置和 schema 进版本库，发布前验证。关键数据有独立于代码回滚的备份和恢复演练。
6. **失败方向。** 认证、授权和支付相关入口在超额或故障时必须拒绝请求。Workers Free 的每日请求上限可以选择 fail open，请求会绕过 Worker；这类入口不使用 Free，并在路由上确认失败模式是关闭。账户级 Workers spending limit 会拒绝新的 Worker 调用，而且作用于该账户上的 Worker，不覆盖 D1、R2、Durable Objects 等独立账单。
7. **例外流程。** 外部数据库、商业 CMS、消费者身份平台、支付、外部发信、外部备份、特殊地域或不兼容运行时，由负责人提交例外，写明原因、供应商、处理的数据、地域、费用、SLA、网络和凭据、导出与退出、替代方案、到期复审。安全与数据负责人批准。违反全 Cloudflare 数据层的方案标记为「混合架构」。

商业支付仍由持牌机构处理。Cloudflare 集成或统一账单不改变实际服务提供方。[6](https://developers.cloudflare.com/hyperdrive/)

## 4. 工具链、渲染与 API

### 4.1 工具链

统一 TypeScript、ES modules 和 Web 标准 API。构建使用与所选框架和 Wrangler 兼容的 Node.js LTS，固定主版本、包管理器和锁文件，CI 使用干净安装。Node 是构建工具。Worker 里的文件 API 即使可用，也不是业务数据的持久磁盘；isolate 回收后不保留模块级可变状态。

新项目的 `compatibility_date` 用开工当日。自 2026-08-04 起，该日期默认带有文档所述的 Node.js 兼容；部分 API 仍是 stub，能导入不代表能调用。升级兼容日期、Wrangler、框架或适配器时，先读兼容变更，再在 workerd 和预发做回归。新配置不手写 `nodejs_compat` 标志来重复这个日期已经开启的行为。[7](https://developers.cloudflare.com/workers/runtime-apis/nodejs/) [8](https://developers.cloudflare.com/workers/configuration/compatibility-dates/)

Wrangler 配置即代码。绑定变更后运行 `wrangler types`，并在 CI 检查生成类型未过期。生产环境配置：

```jsonc
"observability": {
  "enabled": true,
  "logs": { "enabled": true, "head_sampling_rate": 1 },
  "traces": { "enabled": true, "head_sampling_rate": 0.01 }
}
```

只打开顶层 `enabled` 不会打开 traces。环境块如果重写 `observability`，日志和 traces 必须同时保留。`head_sampling_rate` 按流量调整；上面的 traces 采样是起点，不是配额。日志使用 `JSON.stringify` 的结构化字段，用 `console.error` 表示失败。

生产 Worker 在部署前用 `wrangler deploy --dry-run` 看未压缩脚本体积，上限 64 MiB，顶层启动上限 1 秒。SSR 和 Worker 依赖要测真实调用路径。Worker 可以主动建立出站 TCP，不能当作任意入站 TCP 主机。绑定测试使用官方文档当前的 Workers Vitest 集成，在 workerd 中运行；纯函数用普通单测。[7](https://developers.cloudflare.com/workers/runtime-apis/nodejs/) [9](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/) [12](https://developers.cloudflare.com/workers/platform/limits/)

同一账户内 Worker 互调使用 Service Binding。对同一 zone 上另一个 Worker 的普通 `fetch()` 不会到达对方。经 Service Binding 的调用与调用方共享「同时等待响应头」的 6 条连接限额。

### 4.2 静态、SPA 与 SSR

**静态生成**是内容站默认。Astro 或构建流水线产出每个公开 URL 的 HTML、元数据和 sitemap。纯静态输出不需要 Cloudflare adapter，也不需要请求处理脚本。更新变频繁时，先评估按发布事件重建；重建延迟被书面拒绝之后才进入 SSR。[10](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/)

**SPA** 只用于不依赖深层 URL 索引的界面。必须设置 `single-page-application` 并测试深链刷新。不存在的路径会返回入口 HTML 的 200。公开内容站使用多页面真实 404，避免软 404。浏览器不能访问 bindings。[2](https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/) [11](https://developers.cloudflare.com/workers/framework-guides/web-apps/react/)

**SSR** 的准入是第 1 节第 2 问。负责人记录内容新鲜度、首屏性能、缓存策略、成本和回退。用户专属 HTML 使用 `Cache-Control: private, no-store`。公开且与身份无关的响应，才能进入窄范围缓存。SSR 不提高收录的承诺；静态 HTML 同样可索引。

用户专属 SSR 禁止进入共享缓存。Astro 动态渲染使用 Cloudflare adapter。Next.js 的路径以第 1 节第 3 问为准，并记录版本、路由、图片、缓存、Server Actions 和认证的兼容测试。[4](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/) [5](https://developers.cloudflare.com/workers/framework-guides/web-apps/opennext/) [10](https://developers.cloudflare.com/workers/framework-guides/web-apps/astro/)

### 4.3 API 约定

对外或对自有前端的 JSON API：

- 读用 GET 或 HEAD。改变状态用 POST、PUT、PATCH 或 DELETE。GET 不产生副作用。
- 错误体是 `{ "error": "<稳定代码>" }`，带正确的 HTTP 状态。响应中不出现堆栈、SQL、内部路径和密钥。
- 会产生外部副作用或扣减的 POST，接受调用方提供的 `Idempotency-Key`，在 D1 用唯一约束保存结果。
- 列表使用稳定排序和游标。数据量会增长的接口不用页码偏移。
- 只有外部调用方需要冻结协议时才加 `/api/v1`。自有 SPA 可以不版本化，破坏性变更仍走第 12 节的 expand → contract。
- 每个 API 响应带 `Cache-Control: private, no-store` 和 `X-Content-Type-Options: nosniff`，除非该响应被第 9 节明确列为可缓存的公开响应。

## 5. 数据、协调与异步

选定产品之前先写一致性需求。下表是默认映射。

| 已记录的需求 | 选用 | 必须同时接受的性质 |
| --- | --- | --- |
| 关系、约束、事务、会话与账本 | D1 | 单库查询串行；Paid 单库 10 GB 且不能提高；Free 单库 500 MB。绑定在部署时写死 |
| 公开配置、允许延迟生效 | KV | 其他地点可能在 60 秒或更久读到旧值；不存在的键也会被负缓存；经典模式同键写入大约每秒 1 次 |
| 文件和媒体 | 私有 R2 | 不是文件系统，也没有和 D1 的共同事务。自定义域上的 CDN 缓存另算一致性 |
| 单个用户、房间、库存分片的强一致协调 | Durable Objects，每实体一个 ID | 没有跨对象事务。Hibernation 后内存消失 |
| 可重试的任务 | Queues | 至少一次，不保证顺序。单条 128 KB。无死信队列时重试耗尽会删除 |
| 跨分钟或天的多步骤 | Workflows | 等待不占 CPU，步骤和状态单独计费。外部副作用仍要幂等 |
| 多个独立消费者或按保留期重放 | K2 | 按数据量计，不跟踪单条任务的完成状态 |
| 用量、高基数指标、计费事件 | Analytics Engine | 可以丢点或延迟；金额账本仍在 D1 |
| 已批准的外部 SQL | Hyperdrive | 查询缓存默认开启且写入不自动失效 |

官方存储文档把 KV 列为会话和凭证的常见选择，指的是读多、写少、可以接受上述陈旧窗口的数据。本规范里需要立即撤销的会话不用这条建议，权威记录在 D1，见第 10 节。[16](https://developers.cloudflare.com/d1/best-practices/read-replication/) [17](https://developers.cloudflare.com/kv/concepts/how-kv-works/) [72](https://developers.cloudflare.com/workers/platform/storage-options/)

### 5.1 Workers

Worker 跑在 V8 isolate 中。一个 isolate 会交错处理请求，也可能被回收。模块级可变状态不是会话或持久数据。大请求和大响应保持流式，限制并发扇出。

核查日必须计入设计的限额：内存 128 MB/isolate；未压缩脚本 64 MiB；顶层启动 1 秒；Free HTTP CPU 10 毫秒，Paid 默认 30 秒、可配置到 5 分钟。Cron 与队列消费者的墙钟上限 15 分钟；Paid 上，间隔小于 1 小时的 Cron，CPU 默认 30 秒，间隔达到 1 小时的 Cron，CPU 可达 15 分钟。子请求 Free 50 次/调用，Paid 默认 10,000。同时等待响应头的连接最多 6 条，这不是总连接数。`ctx.waitUntil()` 只用于允许失败或可修复的短工作，响应后最多 30 秒。关键后台任务交给 Queues 或 Workflows。HTTP 没有固定墙钟上限，但客户端断开后，未交给 `waitUntil` 的工作可以取消。Cron 使用 UTC，配置变更随部署替换，任务本身必须幂等并持久保存进度。[12](https://developers.cloudflare.com/workers/platform/limits/) [13](https://developers.cloudflare.com/workers/configuration/cron-triggers/) [67](https://developers.cloudflare.com/workers/runtime-apis/context/) [68](https://developers.cloudflare.com/workers/reference/how-workers-works/)

静态资源文件数：Free 每个 Worker 版本 20,000，Paid 100,000；单文件 25 MiB。账户内 Worker 数：Free 100，Paid 默认 500，可申请提高。每个 zone 的 Custom Domain 100 个、Route 1,000 条。这些数字会决定第 7 节何时拆账户或改路由，不是上线后才处理的配额。[12](https://developers.cloudflare.com/workers/platform/limits/)

入站请求体上限跟随 zone 套餐：核查日 Free 与 Pro 100 MB，Business 200 MB，Enterprise 自助最高 5 GB。大文件上传走 R2 预签名，不把文件穿过 Worker。[12](https://developers.cloudflare.com/workers/platform/limits/)

### 5.2 D1

D1 是用户、内容索引、会话、租户目录和账本的权威源。使用 SQLite SQL。每个动态值 `prepare(...).bind(...)`；表名、列名和排序方向用固定白名单。`batch()` 按顺序作为一次事务执行，并且在「每次调用的查询次数」里只算 1 次；「更新 0 行」不一定是 SQL 错误。库存扣减必须检查受影响行数、唯一约束和并发。Paid 每次调用最多约 1,000 条 D1 查询，Free 50 条。单行约 2 MB，绑定参数 100 个，单条 SQL 约 100 KB，单次查询约 30 秒。[14](https://developers.cloudflare.com/d1/platform/limits/) [15](https://developers.cloudflare.com/d1/worker-api/d1-database/) [66](https://developers.cloudflare.com/d1/worker-api/prepared-statements/)

单库串行。查询平均耗时 1 毫秒时，量级大约是每秒 1,000 次查询，其中还有请求开销。出现 overloaded 时，先缩短查询、补索引、用 `batch()` 合并往返；这些做完仍不够，再按第 6.4 节分片。不要用 KV 绕过事务。

读副本：不用 Sessions API 时，查询仍全部打到主库。`withSession()` 提供会话内顺序一致性，包括读己之写，但不等于所有用户看到同一实时状态。跨请求把 bookmark 放在该用户自己的会话里传递。认证和写后必须看到最新数据的路径使用 `first-primary`。副本不另收存储费。主库在单一区域；读延迟来自主库距离时开副本，写路径的延迟来自主库距离时评估 Smart Placement。Smart Placement 改变的是 Worker 运行地点，不改变缓存地点。[16](https://developers.cloudflare.com/d1/best-practices/read-replication/) [73](https://developers.cloudflare.com/workers/configuration/placement/)

Time Travel 对 `version: production` 的库默认开启、不另收费；`wrangler d1 info` 里 `version: alpha` 没有这套能力。保留窗口 Free 7 天、Paid 30 天。恢复会覆盖当前库并取消在途查询。它只恢复这个 D1，不恢复 R2、KV、队列、外部支付或代码。更长留存另行导出并校验。内部维护也可能推进 bookmark，新 bookmark 不等于发生过业务写入。[54](https://developers.cloudflare.com/d1/reference/time-travel/)

### 5.3 KV

KV 用于公开配置、主题、可重建缓存和允许延迟的路由信息。`cacheTtl` 是边缘缓存时间，不是键的过期时间。需要立即撤销的权限、库存、余额、精确计数和支付最终状态，权威源是 D1 或 Durable Objects。经 Durable Object 协调后再写入 KV，读路径仍然是最终一致的。非经典 KV 模式单独验证，不沿用本节数字。[17](https://developers.cloudflare.com/kv/concepts/how-kv-works/) [18](https://developers.cloudflare.com/kv/api/write-key-value-pairs/)

### 5.4 R2

经 binding 的写入、删除和列表对单对象强一致；同 key 并发写，最后完成者胜出。业务表保存对象 key、所有者和校验信息。对象写入和数据库写入之间的失败窗口用补偿、清理任务和对账覆盖。自定义域上的缓存可能继续返回旧对象或旧 404。[19](https://developers.cloudflare.com/r2/reference/consistency/)

私有桶保持私有。小对象由 Worker 鉴权后经 binding 读出。浏览器直传使用短有效期的单对象预签名 URL：R2 binding 不能签发，要在 Worker 内用 S3 凭证（`aws4fetch` 或带 `nodejs_compat` 的 AWS SDK）对 `*.r2.cloudflarestorage.com` 签名。预签名 URL 是 bearer token，在过期前可以重复使用，有效期最长 7 天；生产用分钟级到小时级。它不能用于自定义域，也不支持 HTML 表单 POST。签名时绑定 Content-Type。桶 CORS 只允许确切来源。CORS 不是认证。`r2.dev` 只用于非生产。公开生产对象使用受控自定义域，私人文件不对整个桶开放。[20](https://developers.cloudflare.com/r2/api/s3/presigned-urls/) [21](https://developers.cloudflare.com/r2/buckets/cors/) [22](https://developers.cloudflare.com/r2/buckets/public-buckets/)

S3 兼容是部分能力。实施日重读兼容页；在 versioning 和 replication 被列出之前，不用它们充当备份。生命周期、缓存、强一致和同桶副本都不是历史版本。独立副本、校验、删除保护和恢复演练单独设计。严格 Cloudflare 模式下可以用隔离账户的 R2 副本，这仍不能消除 Cloudflare 级故障。[23](https://developers.cloudflare.com/r2/api/s3/api/) [24](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)

### 5.5 Durable Objects

每个实体一个稳定 ID，使用 SQLite-backed 存储。不为整个站点建一个对象。单线程不会让跨 `await` 和外部调用自动变成事务；多语句业务用存储事务。内存只放可重建缓存。跨对象没有全局事务。类的重命名、迁移和删除按官方多阶段流程审查；删除可以永久删除数据，部署回滚不能恢复已删命名空间。[25](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/) [26](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) [28](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/)

WebSocket 使用 Hibernation API。休眠后内存消失，连接上下文放 attachment，权威状态写入存储。客户端支持断线重连。DO 的 jurisdiction 是放置控制，不等于其他地区的 Worker 不能访问它。[27](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) [65](https://developers.cloudflare.com/durable-objects/reference/data-location/)

需要跨地点严格计数（精确配额、不能超卖的库存令牌）时，用按键拆开的 Durable Object 做计数器。普通的近似限流用第 10 节的 Rate Limiting binding，不为此引入对象。

### 5.6 Queues、Workflows 与 K2

Queues 至少投递一次，不保证顺序。消息带稳定业务事件 ID、schema 版本和最少字段。副作用确认之后再逐条 `ack`。暂时失败用退避 `retry`。配置有限重试、死信队列、告警和受控重放。未配置死信队列时，重试耗尽的消息被删除。死信队列没有消费者时，DLQ 文档写明 4 天后删除；队列保留期本身 Paid 可配置、最长 14 天，Free 固定 24 小时。单队列大约每秒 5,000 条消息，积压上限 25 GB。死信队列不是归档系统。[29](https://developers.cloudflare.com/queues/reference/delivery-guarantees/) [30](https://developers.cloudflare.com/queues/configuration/batching-retries/) [31](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/) [74](https://developers.cloudflare.com/queues/platform/limits/)

可靠事件的写法：在同一个 D1 事务里写入业务变更和 outbox，再由可重试发布器发送；发送成功但标记失败会造成重复，消费者按业务事件 ID 去重。D1 与 Queues 没有跨服务事务。

Workflows 管理长时间等待、重试和补偿。每个有副作用的 step 使用稳定幂等键。由 Queue 触发时，先确认确定性实例已经创建或已经存在，再 `ack`。崩溃窗口靠实例 ID、唯一约束和补偿，不靠跨产品原子提交。[32](https://developers.cloudflare.com/workflows/build/sleeping-and-retrying/) [33](https://developers.cloudflare.com/workflows/build/trigger-workflows/)

K2 用于高吞吐、多订阅者、可重放的事件流。每个订阅者独立读完全部记录。单条任务的重试和死信仍然用 Queues。核查日 K2 是 Public Beta，需要 Workers Paid；Beta 期间每账户存储上限 10 GB，保留期最长 30 天，更高额度需要申请。这个额度装不下事件流时，不要把它选进方案。[75](https://developers.cloudflare.com/k2/)

## 6. 参考架构

组件可以删，不可以为了对称往上加。

### 6.1 纯静态内容站

```text
编辑 / 审核 → Git → 构建 Astro → Workers Static Assets
访客 → DNS / HTTPS / WAF → HTML、CSS、JS
```

每个站点独立的构建产物、Worker 或纯资产、域名和发布权限。私有内容不进入 `dist`。预览限制访问并设置 `noindex`；`noindex` 不是访问控制。不引入 D1、R2、Hono 或 Paid 专属产品。CI 和仓库若在第三方，记为开发供应链。生成文件数按第 5.1 节的单版本上限估算，接近上限时拆站点或改用分页数据源，不把超额当成上线后的配额事故。

### 6.2 纯前端应用，以及静态壳加 API

```text
浏览器 → DNS / HTTPS / WAF → Workers Static Assets
                             └─ /api/* → Hono
                                          ├─ D1：用户、内容、对象引用
                                          ├─ R2：私有文件
                                          └─ KV：允许旧值的公开配置（可选）
管理员 → Access → 应用层再做管理员授权
```

纯前端停在资产层。一旦有 API：bindings 只在 Worker 内读取。创建文件时先做用户或租户授权和大小限制，再写 R2、再写 D1，并为失败窗口做补偿和对账。身份可以自建在 D1；真实支付和其 webhook 是外部依赖。

### 6.3 异步与实时

```text
浏览器 → Worker API → 同一 D1 事务：业务状态 + outbox → 发布器 → Queues
                                                         └─ 消费者 → Workflows → 外部副作用
浏览器 → 按实体 ID → Durable Object（SQLite） → WebSocket 客户端
失败 → 有限重试 → 死信队列 → 告警 → 人工检查 → 幂等重放
```

Durable Objects 只协调自己的实体。小站点没有重试或实时需求时，不引入队列和对象。

### 6.4 复杂 SaaS

默认是一套由本团队部署的应用服务多个租户，而不是每个租户一个 Worker。

```text
浏览器
  → 平台域名（Worker Custom Domain）
    或客户域名（Cloudflare for SaaS custom hostname）
  → WAF、Turnstile、Rate Limiting
  → 一个 Worker：静态资源 + Hono API + 队列消费者
        ├─ 一个 D1：所有业务表含 tenant_id
        ├─ 一个私有 R2：对象键以 tenants/{tenantId}/ 开头
        ├─ Analytics Engine：用量事件（可选）
        └─ Durable Object：仅当某个实体需要强一致协调，ID 含 tenantId
员工后台 → Access → 应用层角色和审计
```

**租户数据。** 每一张业务表都有 `tenant_id`。唯一约束和查询都带租户，例如 `(tenant_id, business_key)`。租户 ID 来自已校验的会话，不来自调用方自行指定的字段。对象键前缀同样来自会话中的租户。这是共享库方案的隔离边界，应用代码之外没有第二道自动的行级隔离。

**分片。** 从第一个 D1 开始。出现 overloaded、索引和 `batch()` 已经不能把写等待压回预算，或单库达到 5 GB 的团队复审线时，做固定分片。平台硬顶是 10 GB，不能调高。做法是在部署配置里绑定有限个库（个数在设计里写死），用目录表把 `tenant_id` 映射到分片。新租户在创建时分配分片。运行时不能为每个租户创建一个新的 D1 binding；binding 大约 5,000 的上限也不能当作「一租户一库」的计划。跨分片没有事务。账户级报表从 Analytics Engine 或异步汇总来，不跨库实时 JOIN。只有书面隔离要求禁止共享表，并且租户数有上界、增加租户可以接受一次部署时，才使用一租户一库。

**何时拆成多个 Worker。** 默认一个脚本同时提供资产、API 和队列消费。出现下列情况之一再拆，并用 Service Binding 互调：消费者需要不同的 CPU 或墙钟配置；支付 webhook 的密钥不应出现在面向用户的 Worker 上；静态文件数接近第 5.1 节上限；发布节奏必须分开。

**客户域名和客户代码。** 客户只是用自己的域名访问这套应用：Cloudflare for SaaS 的 custom hostname，校验域名控制权后再签发证书。核查日该产品随非 Enterprise 套餐提供，Enterprise 是附加项，以合同为准。apex 代理是 Enterprise 附加能力；不能假设每个客户的根域都能 CNAME。客户要运行自己的代码：Workers for Platforms。两件事都要就两个产品一起用，它们不是同一个开关。[76](https://developers.cloudflare.com/cloudflare-for-platforms/cloudflare-for-saas/) [77](https://developers.cloudflare.com/cloudflare-for-platforms/workers-for-platforms/)

**账本。** 可计费用量写入 Analytics Engine 做聚合。发票、余额和已入账金额的权威记录在 D1，用幂等键防止重复入账。Analytics Engine 不是账本。

**缓存。** 多租户 Worker 默认不开启 Workers Cache。若开启，缓存键默认不含主机名，见第 9 节；租户必须进入路径或 `ctx.props`，并用两个租户做泄露测试。

## 7. 多站点、环境和账号

**仓库。** 多个站点默认放在同一个 monorepo：`apps/<site>/` 放应用、Wrangler 配置、迁移和资产，`packages/` 放共享 UI、类型和审查过的工具。每站单独 build、test、deploy。共享包变更要触发受影响的站点。每站可以独立回滚。不用一个 Worker 挂载多个互不相关站点的资产。一个 SaaS 产品用一个应用目录，不按租户拆目录。站点数量、权限或合规隔离使单仓不合算时再拆仓，规范保持一致。

**环境。** 每站至少有本地、受控预览或预发、生产。预览使用独立域名、D1、KV、R2、队列、服务绑定和 secrets，或者不接任何持久资源。预览不触发生产邮件、支付、定时任务或 webhook。不能证明绑定和访问都隔离时，不做有状态的 PR 预览，改用固定的 staging。Workers Previews 是否隔离所绑定的资源，以实施日文档为准；不能证明隔离，就不许指向生产。测试数据虚构或脱敏。Wrangler 的 environment 是独立 Worker；bindings、`vars`、secrets 不从顶层继承，目标环境里显式配置。部署前核对资源 ID，不只核对 binding 名。`remote` binding 会改真实资源并产生费用。[40](https://developers.cloudflare.com/workers/wrangler/environments/) [41](https://developers.cloudflare.com/workers/configuration/secrets/)

**账户。** 同一产品的多个环境可以先放在一个账户，用独立资源、zone、最小权限 token 分开。下列任一出现时拆账户：客户合同要求故障或权限隔离；生产 token 无法与预览 CI 分开；Worker 数量接近第 5.1 节的账户上限。拆账户会增加最低消费和管理成本，按威胁模型批准。配置所有者、备份所有者、事件响应人和账单负责人。生产部署 token 不给 PR、fork 或日常开发。资源名、UUID、域名和负责人登记在资产清单。

## 8. 可实施最小示例：静态前端 + Hono + D1 + R2

本章是隔离环境教材，用来走通绑定、迁移和失败补偿。它没有用户身份、授权、CSRF、配额、滥用防护和完整对账，**不能开放到生产或公网匿名写入**。生产要先补齐第 10 节。D1 与 R2 之间的写入不是事务。

示例是单页工具，所以使用 SPA 回退。内容站不要复制 `not_found_handling`。示例不开启 Workers Cache。`compatibility_date` 固定在本示例的测试日，新项目用开工当日。

以下命令从单个新项目目录执行，使用 npm 和与所装 Vite、Wrangler 兼容的 Node.js LTS。`package-lock.json` 提交，CI 使用 `npm ci`。Vite 使用默认约定：根目录 `index.html` 构建到 `dist/`，本示例不需要额外的 Vite 配置。

### 8.1 创建项目与资源

```bash
mkdir catalog-demo && cd catalog-demo
npm init -y
npm install hono
npm install --save-dev vite typescript wrangler @cloudflare/workers-types
npm pkg set 'scripts.build=vite build' \
  'scripts.check=tsc -p tsconfig.worker.json && tsc -p tsconfig.client.json' \
  'scripts.dev=wrangler dev --local'
mkdir -p src migrations
```

登录目标账户，创建两个不同的远程 D1 和两个 R2 桶。桶名冲突时，命令和配置一起改。命名要保证站点和环境互不重名。

```bash
npx wrangler login
npx wrangler d1 create catalog-demo-staging-db
npx wrangler d1 create catalog-demo-production-db
npx wrangler r2 bucket create catalog-demo-staging-objects
npx wrangler r2 bucket create catalog-demo-production-objects
```

用两次 D1 create 输出的 UUID 替换 `<STAGING_D1_UUID>` 和 `<PRODUCTION_D1_UUID>`。`staging.example.com` 与 `www.example.com` 换成同一目标账户里已启用 zone 上的两个不同主机名，并确认证书和 DNS。`catalog-demo-local-db`、`catalog-demo-local-objects` 和全零 UUID 只给本地模拟，不创建云端资源，也不用来部署。

### 8.2 `wrangler.jsonc`

`observability` 写在顶层，环境会继承。若某个环境重写该字段，日志和 traces 要一起保留。示例把 traces 采样设为 1，只因为流量极小；生产从第 4.1 节的采样起点算账单，不要照抄 1。2026-11-08 的本地跑通不包含这个字段；它是 2026-11-14 按生产要求补上的。


### 8.4 后端：`src/worker.ts`

```ts
import { Hono } from 'hono';

type Env = { DB: D1Database; OBJECTS: R2Bucket };
type Note = { id: string; created_at: string };
const app = new Hono<{ Bindings: Env }>();
const MAX_BYTES = 64 * 1024;

// 不信任 Content-Length；逐块读取并在达到上限时停止。
async function readBounded(request: Request): Promise<Uint8Array | null> {
  if (!request.body) return new Uint8Array();
  const reader = request.body.getReader();
  const chunks: Uint8Array[] = [];
  let total = 0;
  try {
    while (true) {
      const { done, value } = await reader.read();
      if (done) break;
      total += value.byteLength;
      if (total > MAX_BYTES) {
        await reader.cancel();
        return null;
      }
      chunks.push(value);
    }
  } finally {
    reader.releaseLock();
  }
  const result = new Uint8Array(total);
  let offset = 0;
  for (const chunk of chunks) {
    result.set(chunk, offset);
    offset += chunk.byteLength;
  }
  return result;
}

app.use('/api/*', async (c, next) => {
  await next();
  c.header('Cache-Control', 'private, no-store');
  c.header('X-Content-Type-Options', 'nosniff');
});

app.get('/api/health', (c) => c.json({ ok: true }));

app.get('/api/notes', async (c) => {
  const result = await c.env.DB
    .prepare('SELECT id, created_at FROM notes ORDER BY created_at DESC LIMIT 20')
    .all<Note>();
  return c.json({ notes: result.results });
});

app.post('/api/notes', async (c) => {
  const mediaType = (c.req.header('Content-Type') ?? '').split(';')[0].trim().toLowerCase();
  if (mediaType !== 'text/plain') return c.json({ error: 'text/plain required' }, 415);
  const bytes = await readBounded(c.req.raw);
  if (bytes === null) return c.json({ error: 'too large' }, 413);
  if (bytes.byteLength === 0) return c.json({ error: 'empty body' }, 400);

  const id = crypto.randomUUID();
  const key = `notes/${id}.txt`;
  await c.env.OBJECTS.put(key, bytes, {
    httpMetadata: { contentType: 'text/plain; charset=utf-8' }
  });
  try {
    await c.env.DB.prepare('INSERT INTO notes (id, created_at) VALUES (?1, ?2)')
      .bind(id, new Date().toISOString()).run();
  } catch (error) {
    // 尽力补偿；真实系统还须定期清理无法记录的孤儿对象。
    try { await c.env.OBJECTS.delete(key); }
    catch { console.error(JSON.stringify({ message: 'object cleanup failed', id })); }
    console.error(JSON.stringify({ message: 'database insert failed', id }));
    return c.json({ error: 'save failed' }, 500);
  }
  return c.json({ id }, 201);
});

app.get('/api/notes/:id', async (c) => {
  const id = c.req.param('id');
  if (!/^[0-9a-f-]{36}$/i.test(id)) return c.json({ error: 'not found' }, 404);
  const note = await c.env.DB.prepare('SELECT id FROM notes WHERE id = ?1 LIMIT 1')
    .bind(id).first<{ id: string }>();
  if (!note) return c.json({ error: 'not found' }, 404);
  const object = await c.env.OBJECTS.get(`notes/${id}.txt`);
  if (!object) return c.json({ error: 'object missing' }, 404);
  // 直接返回 Response 时，中间件未必能写回头；这条路径自己带上。
  return new Response(object.body, {
    headers: {
      'Content-Type': 'text/plain; charset=utf-8',
      'Cache-Control': 'private, no-store',
      'X-Content-Type-Options': 'nosniff'
    }
  });
});

app.notFound((c) => c.json({ error: 'not found' }, 404));
export default app;
```

```ts
export {};

type Note = { id: string; created_at: string };
const form = document.querySelector<HTMLFormElement>('#form')!;
const input = document.querySelector<HTMLTextAreaElement>('#text')!;
const list = document.querySelector<HTMLUListElement>('#notes')!;
const status = document.querySelector<HTMLParagraphElement>('#status')!;
const content = document.querySelector<HTMLPreElement>('#content')!;

async function refresh(): Promise<void> {
  const response = await fetch('/api/notes');
  if (!response.ok) throw new Error('读取列表失败');
  const data = await response.json() as { notes: Note[] };
  list.replaceChildren();
  for (const note of data.notes) {
    const item = document.createElement('li');
    const button = document.createElement('button');
    button.type = 'button';
    button.textContent = `${note.created_at} ${note.id}`;
    button.addEventListener('click', async () => {
      try {
        const res = await fetch(`/api/notes/${encodeURIComponent(note.id)}`);
        if (!res.ok) throw new Error('读取正文失败');
        content.textContent = await res.text();
      } catch (error) {
        status.textContent = error instanceof Error ? error.message : '请求失败';
      }
    });
    item.append(button);
    list.append(item);
  }
}

form.addEventListener('submit', async (event) => {
  event.preventDefault();
  try {
    const response = await fetch('/api/notes', {
      method: 'POST', headers: { 'Content-Type': 'text/plain; charset=utf-8' },
      body: input.value
    });
    if (!response.ok) throw new Error(`保存失败：${response.status}`);
    input.value = '';
    status.textContent = '已保存';
    await refresh();
  } catch (error) {
    status.textContent = error instanceof Error ? error.message : '请求失败';
  }
});
refresh().catch(() => { status.textContent = '读取列表失败'; });
```

## 9. DNS、缓存、内容与 SEO

**DNS/TLS。** Worker 是源站时用 Custom Domain，覆盖该主机名的全部路径。已有源站前面挂 Worker 时用 Routes，并确认活动 zone 和橙云。存在外部源站时，生产使用可验证源站证书的 Full (strict)，关闭源站直连。DNS-only 会暴露源站地址。apex 与 `www`、证书和重定向逐个测试。同一 zone 的 Custom Domain 超过 100 个时，改用 Route 或 Cloudflare for SaaS，不把超限留到上线当天。[42](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/) [44](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/)

**两套缓存。** 未开启 Workers Cache 时，命中的静态资源由资产层返回，不执行 Worker，这些请求不计 Worker 请求费。带哈希的构建产物用长缓存，HTML 和 manifest 用短缓存或重新验证。先让新资源可访问，再切换入口，并按 URL 精确 purge。不覆盖同名不可变文件。

Workers Cache（`cache.enabled`）是另一层：它在 Worker 执行前返回缓存，zone 的 Cache Rules、Page Rules 和扩展名默认缓存对它无效。缓存键默认包含路径、入口、`ctx.props` 和 Worker 版本，不包含主机名；查询串是否进入键，启用前重读 cache keys 页。因此一个 Worker 服务多个主机或租户时，默认会把相同路径当成同一份响应。启用条件同时满足：响应公开且与身份、租户无关；租户或主机已经进入路径或 `ctx.props`；每条响应，包括错误，都写了明确的 `Cache-Control`。未写 `Cache-Control` 时，平台可能按启发式新鲜度缓存。`private` 不进入共享缓存。`Set-Cookie` 和 `Authorization` 会触发绕过，这只是纵深防御，泄露测试仍用两个身份、两种语言和两个租户各做一次。

开启 Workers Cache 之后，缓存命中仍按 Worker 请求计费，命中不收 CPU；原本免费的静态资源请求和 Service Binding 调用也会按 Worker 请求计费。只为少付 CPU 就开启，可能多付请求费。Cache API 是数据中心本地缓存，没有请求合并；Workers Cache 不能满足需求时才用它。[45](https://developers.cloudflare.com/cache/how-to/cache-rules/) [46](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/) [47](https://developers.cloudflare.com/workers/runtime-apis/cache/) [70](https://developers.cloudflare.com/workers/cache/)

个性化页面、账户、订单和租户 API 使用 `Cache-Control: private, no-store`。

**CMS。** 小站用 Git 管理 Markdown/MDX 或结构化内容。需要多人、角色、草稿、媒体或定时发布时，用 Worker + D1 + R2 做最小后台，Access 保护员工入口，应用层做角色、审计和发布版本。这不是 Cloudflare 提供的完整 CMS。商业 SaaS CMS 按第 3 节登记数据、地区、webhook、重试、费用和退出导出。

**国际化。** 语言有可分享的 URL，例如 `/en/`、`/fr/`。不按 IP、Cookie 或浏览器语言无条件改写爬虫请求。各语言版本有正确的 `lang`、互指的 `hreflang` 和 self-canonical。缓存键区分语言、区域和租户。

**SEO。** 每个公开页面在 HTML 里输出标题、description、canonical、正文和可抓取的内部链接；按需提供 sitemap 和 robots.txt。预览和私密页限制访问并 `noindex`。迁移和不存在的页面使用真实的 301/308 和 404/410。发布后检查状态码、源 HTML、canonical 和语言标签。Crawler Hints 只是通知辅助。[48](https://developers.cloudflare.com/cache/advanced-configuration/crawler-hints/)

## 10. 身份、支付、邮件与应用安全

**消费者身份。** Access 是员工和内部应用的访问控制，不提供消费者注册、找回和账户生命周期。消费者身份默认自建在 D1：高熵不透明会话 ID、可撤销的服务端记录、密码或通行密钥、账户恢复、封禁、删除和客服流程。自建意味着这些控制由团队实现并验证。外部 IdP 走第 3 节例外。Access 可以放在预发和员工后台前面，策略要实际验证；它不替代应用内的角色和对象授权。[49](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/)

**会话存在哪里。** 需要退出、封禁或权限变更立即生效时，权威会话在 D1，每次请求读 D1。只有书面接受大约 60 秒的撤销延迟，并且同一键的写入低于 KV 的写入速率时，才可以把会话放在 KV，并把这个延迟写进威胁模型。官方存储页推荐 KV 存会话，适用的是后一种；本规范的默认是前一种。

**密码。** Free 的 10 毫秒 CPU 不够做口令哈希。Paid 上使用 Web Crypto，并在预发测量 CPU；测不进预算就改用通行密钥或已批准的 IdP。不在 Worker 里引入未经测量的 bcrypt 或 Argon2。

**Cookie 与浏览器。** Cookie 使用 `Secure`、`HttpOnly`、适当的 `SameSite`、最小作用域和有效期，可用时用 `__Host-` 前缀。状态变更校验 CSRF token 和 Origin。SameSite 是纵深防御。所有接口按用户、租户和对象校验。跨源 CORS 只放行确切 origin、方法和头；带凭据时不使用通配符，并设置 `Vary: Origin`。CORS 不完成鉴权，也不完成 CSRF 防护。

跨源请求若在 Access 后面，浏览器的 OPTIONS 预检通常不带 Access cookie。按 Access 的 CORS 配置放行预检；请求到达源站后仍由源站执行 CORS 和业务授权。[69](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/cors/)

**限流分层。**

| 层级                    | 用在               | 必须接受的性质                                                                                                                                                                                           |
| --------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| WAF 速率限制              | 登录、表单、上传入口的粗粒度防护 | 计数可能延迟，规则挂在 zone 上                                                                                                                                                                                |
| Turnstile             | 匿名写入和注册          | token 由后端 Siteverify 校验，核对 hostname 和 action；单次使用，有效期以实施日文档为准。secret 不进浏览器 [51](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/)                                  |
| Rate Limiting binding | 按用户、租户或路由的应用限额   | 按 Cloudflare 地点近似计数，地点之间不合并。`period` 只能是 10 或 60 秒。Wrangler 4.36.0 及以上。绑定不在仪表盘单独展示，用日志或 Analytics Engine 观察 429 [71](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) |
| Durable Object        | 跨地点都不能超的配额       | 按键拆对象，计数持久化在该对象内                                                                                                                                                                                  |

IP 可以做辅助信号，不作为唯一的限额键；载波级 NAT 和隐私中继会让许多用户共享一个地址。精确的业务配额，例如「这个租户本月的额度」，在 D1 或 Durable Object 里结算，不在 WAF 里结算。

**支付。** 真实收款走第 3 节例外。优先使用服务商托管的支付页面或组件，Worker 和日志不接触原始卡数据。PCI 范围按合同确认。Webhook 校验签名、时间窗和事件 ID，异步处理、去重，并以服务商的最终状态对账。前端跳转回站不是付款成功。

**邮件。** Email Routing 处理入站。Email Sending 在核查日仍是 Beta，任意收件人需要 Workers Paid；发往账户内已验证地址在 Free 和 Paid 上不另收费。验证码、收据和营销邮件分开管理域名验证、退信、抑制名单、退订和声誉。发送用 Queues 或 Workflows 做幂等重试。外部邮件商属于外部依赖。[52](https://developers.cloudflare.com/email-service/) [53](https://developers.cloudflare.com/email-service/platform/pricing/)

**Secrets 和隐私。** 密钥放在对应环境的 Worker Secrets；跨多个 Worker 一次轮换时才用 Secrets Store。生产密钥只由受控发布流程注入。轮换、吊销、所有者和过期要有记录。日志不包含 cookie、Authorization、预签名 URL、完整邮件、支付数据和密钥。个人数据写明用途、访问范围、保留期、删除和导出。数据驻留由合规负责人评估；DO jurisdiction 和 D1 的位置提示都是放置控制，不是「其他地区的计算不会发生」。[41](https://developers.cloudflare.com/workers/configuration/secrets/) [65](https://developers.cloudflare.com/durable-objects/reference/data-location/)

## 11. 备份、恢复、RPO 与 RTO

每个生产站点按数据类别指定负责人。RPO 是最多可接受的数据丢失时长，RTO 是从故障到服务恢复的目标时长，由业务批准。至少分别为 D1、R2、配置与密钥、内容仓库和第三方状态写下目标。严格 Cloudflare 范围内的多账户副本不能消除 Cloudflare 级故障；要求供应商级独立时，批准外部备份例外。

Time Travel 的窗口和覆盖行为见第 5.2 节。备份若放在 R2，还要为那个桶设计独立副本。R2 的备份对象包括对象、元数据和清单，并验证复制、访问隔离和删除保护。D1 与 R2 的副本不是同一时点：用清单或可重放事件找出「库有引用、对象缺失」和「对象还在、引用没有了」。支付以外部事实对账，不随 D1 恢复自动回退。[19](https://developers.cloudflare.com/r2/reference/consistency/) [23](https://developers.cloudflare.com/r2/api/s3/api/)

**演练：**隔离写入和消费者；记录故障时刻、版本和恢复目标；在隔离环境恢复 D1 和对象，抽查引用和关键状态；按批准的时间点恢复生产或切换到准备好的资源；按幂等规则处理恢复点之后的事件和支付；逐步放量。每季度至少一次，权限、架构或备份方案大改之后加测。RPO 和 RTO 只有演练结果落在目标内才算达标。

## 12. 开发流程、迁移与回滚

1. **立项。** 填写第 16 节。确认数据分类、一致性、地域、流量和预算。只创建第 2 节该类型需要的资源。
2. **开发。** 固定工具链和锁文件。本地 workerd 和模拟资源优先。需要真实平台行为时只连隔离的 staging，并审查 `remote`。提交前做类型、lint、绑定测试和秘密扫描。
3. **预发。** 干净构建，迁移，部署到 Access 后面的独立环境。用 Workers runtime 验证，不只用 Node 的 dev server。检查权限、CORS、重复消息、失败恢复、路由和缓存泄露。
4. **发布。** 受保护分支、审批、最小权限部署 token、单一发布入口。记录 commit SHA、依赖和运行时版本、Worker 版本、账户和绑定、迁移序号、变更人和回滚负责人。先部署向后兼容的 schema，再发布应用。放量能力以账户实际功能为准。
5. **回滚。** 先停止放量。确认旧 Worker 与当前 schema 兼容后再回滚代码。数据已经改变时，做前向修复、补偿或经审批的恢复。代码回滚不还原 D1、R2 和已发送的消息，也可能因为旧版依赖的资源已被删除而失败。[55]

**D1 迁移。** 已应用的文件只追加、不修改。每次先 `list`，再 `--local`，然后 staging `--remote`，审批后再 production `--remote`。单条失败不表示此前成功的迁移已撤销。破坏性变更使用 expand → 兼容读写 → 分批回填并验证 → 等旧版本退出 → contract。准备前向修复或演练过的恢复，不假设存在自动的 down migration。[43](https://developers.cloudflare.com/d1/reference/migrations/)

**测试按类型取舍。** 未启用的产品不编造用例，在记录里写「不适用」。启用了的部分至少覆盖：SQL 参数化、受影响行数、迁移与旧版本兼容；KV 的旧值和负缓存；R2 私有访问和跨存储失败；队列的重复、乱序、重试和死信；Workflow 重放；Durable Object 的重启、休眠和热点；越权、CSRF、CORS；静态或 SSR 的路由、404、SEO 和跨用户缓存；安全路径在超额时拒绝而不是绕过。使用测试邮箱和支付 sandbox。

**CI。** 同一个 Worker 只选一个生产发布控制面：Workers Builds 或外部 CI。不可信 PR 没有生产 token。构建阶段以第 8 节项目为例：

```bash
npm ci
npm run check
npm run build
npx wrangler deploy --dry-run --env staging
```

远程迁移和 deploy 是后续有审批的独立阶段。固定第三方 Action 的版本并审查权限。构建产物和预览不含 secrets 和真实客户数据。Git 托管方记入供应链。[56](https://developers.cloudflare.com/workers/ci-cd/builds/)

## 13. 可观测性与事件响应

结构化日志至少包含时间、环境、站点、Worker 版本、request ID、路由、状态、耗时和错误类别；异步路径加上事件 ID、Workflow 实例 ID 和脱敏后的租户或对象标识。不记录认证头、完整 URL 中的敏感参数和请求正文。日志有 256 KB/请求的上限，超出部分不会进入该请求的日志。核查日 Workers Logs：Free 每日 200,000 条、保留 3 天；Paid 每月含 2,000 万条、超出每百万 0.60 美元、保留 7 天。自 2026-12-01 起改为 Observability 定价，实施时重读。[57](https://developers.cloudflare.com/workers/observability/logs/) [58](https://developers.cloudflare.com/workers/platform/pricing/)

告警覆盖：请求量、异常的 5xx/4xx、P95/P99、CPU、内存和限额错误、D1 慢查询、R2 失败、KV 错误、Durable Object 热点、队列积压、最老消息年龄、重试和死信、Workflow 失败、缓存的跨用户异常、预算。阈值来自预发基线和业务目标。值班手册包含用户影响、熔断、暂停消费、限流、回滚、恢复、供应商联络和复盘。

**定期审计：**账户和 zone 的所有权与 MFA；生产 token 的权限和有效期；预览是否指向生产；域名、证书和旁路源站；Access 与应用授权；secrets 和依赖漏洞；对象公开状态、CORS 和生命周期；导出和删除；备份和演练；Cron、队列和死信；缓存键、purge 和泄露测试；成本、套餐和地域；例外是否到期；发布记录。至少每季度一次，重大变更后立即复查。

## 14. 成本与配额

按账户和账期核算，不按站点孤立估算：订阅或最低消费、Worker 请求和 CPU、D1 行读写与存储、KV、R2 存储和 Class A/B、Queues、Durable Objects、Workflow 步骤和状态、日志，以及可选的媒体、AI、浏览器和外部供应商。包含量在账户内共享。多个账户分别计算。每个站点记录占用、峰值、重试和成本归属。

核查日 Workers Paid 最低每账户每月 5 美元，含每月 1,000 万请求和 3,000 万 CPU 毫秒；超出部分为每百万请求 0.30 美元、每百万 CPU 毫秒 0.02 美元。未开启 Workers Cache 时，静态资源请求免费。官方示例：每月 1,500 万次 Worker 请求、平均 7 毫秒 CPU，请求超出 500 万计 1.50 美元，CPU 超出 7,500 万毫秒计 1.50 美元，加最低消费为 8 美元；不含 D1、R2 和税。同一请求量若 80% 是免费静态资源、其余未超出包含量，则只有 5 美元最低消费。开启 Workers Cache 后，命中和静态资源都按请求计费，CPU 只在 Worker 真正执行时计费。[58](https://developers.cloudflare.com/workers/platform/pricing/) [70](https://developers.cloudflare.com/workers/cache/)

D1 按扫描和写入的行计费，不是按返回行；索引能减少扫描，也会放大一部分写入。KV 读不存在的键也计操作，写入的单价显著高于读取。R2 的互联网出站免费，存储和请求不免费。Queues 按消息以及每 64 KB 分块计读写删，重试和死信都会增加操作。Durable Objects 按请求、活跃时间和存储计。Workflow 另计步骤和状态。Free 的日额度用尽会导致调用失败，不能当成持续服务。设置预算负责人、告警、降级和上限。Workers spending limit 的连坐范围见第 3 节。[58](https://developers.cloudflare.com/workers/platform/pricing/) [59](https://developers.cloudflare.com/d1/platform/pricing/) [60](https://developers.cloudflare.com/r2/pricing/) [61](https://developers.cloudflare.com/queues/platform/pricing/) [62](https://developers.cloudflare.com/durable-objects/platform/pricing/) [63](https://developers.cloudflare.com/workflows/reference/pricing/)

全球网络不等于中国大陆可用。China Network 是单独订阅，有产品、合同、备案和地域条件。大陆访问是目标时单独审批，并按运营商和地区实测。[64](https://developers.cloudflare.com/china-network/)

## 15. 上线验收与禁止

### 15.1 每个上线都要有的项

- [ ] 第 16 节已填写；类型、数据分类、外部依赖、成本预算和账户计划已核对。
- [ ] DNS、HTTPS、Custom Domain 或 Route、证书、apex/`www`、本类型应有的 404 或 SPA 深链已验证。
- [ ] 本地、预览、staging、生产的资源和密钥隔离；预览有访问控制、`noindex`，且不会打到生产支付或邮件。
- [ ] 安全相关入口在超额时拒绝请求，不使用会绕过 Worker 的 fail open。
- [ ] 生产配置打开了日志和 traces；告警、预算、值班人、事故手册和回滚负责人已指定。
- [ ] 本类型未使用的产品已在模板里写明「不适用」和理由。

### 15.2 启用了才验收

- [ ] 身份、对象权限、会话撤销、CSRF、CORS、WAF、限流、Turnstile 的后端校验、秘密扫描。
- [ ] D1 的参数化、索引、容量、Sessions API 和 bookmark；R2 的私有或公开策略、预签名、CORS、生命周期。
- [ ] 队列的重复、乱序、重试和死信；Workflow 的幂等和补偿；Durable Object 的热点和休眠恢复。
- [ ] 静态资源、私有响应、语言和租户之间的缓存隔离。若开启 Workers Cache：缓存键含租户，错误响应也有明确的 `Cache-Control`，账单按「静态资源改为计费」复算过。
- [ ] SEO 的状态码、canonical、hreflang、robots 和 sitemap。
- [ ] 迁移、旧版本兼容、代码回滚和数据前向修复；D1 与 R2 分开的备份和演练记录，RPO/RTO 有实测。

### 15.3 禁止

- 禁止把 isolate 内存、`waitUntil`、Cron 或出站 TCP 当作持久会话或常驻服务器。
- 禁止用 KV 作为立即撤权、库存、余额、支付状态或精确计数的唯一权威源。
- 禁止把 R2 `r2.dev` 当作生产域名；禁止用 R2 强一致、生命周期或 D1 Time Travel 代替独立对象备份。
- 禁止假设队列有序或恰好一次；禁止在副作用确认前 `ack`；禁止没有死信队列和告警却把失败当成已保存。
- 禁止在多主机或多租户 Worker 上开启 Workers Cache，除非租户已经进入缓存键并完成泄露测试。
- 禁止只靠 CORS、Access、Turnstile、WAF、Rate Limiting 或前端判断完成授权。
- 禁止预览、测试或不可信 CI 使用生产写绑定、生产 secret、真实支付和发信凭据。
- 禁止在运行时为每个租户创建 D1 binding，或在一个 Durable Object 上承载全站流量。
- 禁止未经审查执行破坏性迁移，或把 Worker rollback 说成数据恢复。
- 禁止把 Hyperdrive 说成数据库托管，把 Access 说成消费者身份平台，把支付、IdP 或商业 CMS 说成纯 Cloudflare 原生。
