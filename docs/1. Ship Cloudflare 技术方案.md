## 1. 要做成什么

Ship Cloudflare 是一套放在同一个仓库里的部署模板。克隆之后可以直接本地跑、可以按模板部署到 Cloudflare，也可以在同一套约定上继续加插件。

本期两个模板对应规范第 2 节的两行：

| 模板        | 规范类型         | 用户拿到的东西                                                                                                                                        |
| ----------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `apps/web`  | 纯静态内容站     | 用 Astro 在构建时生成的内容站，可以带一个不保存数据的简单工具页。部署为 Workers Static Assets。没有 Worker 脚本，没有数据库，没有本团队持有的用户数据 |
| `apps/saas` | 复杂 SaaS 的骨架 | 一个 Worker：可被索引的公开页面、登录后才使用的应用壳、只读 API、一个 D1。写接口默认拒绝，等认证插件接上再打开                                        |

以后每个插件是一个独立包。应用在一个静态列表里显式启用它。插件可以带 Drizzle 表、SQL 迁移、Hono 路由和 SPA 页面。绑定（D1、R2、KV、队列）写在该应用的 `wrangler.jsonc` 里，由清单检查，不在运行时创建。

## 2. 对照 TinyShip：留下的结构和改掉的结构

TinyShip（`/Users/boya/Projects/OpenSource/tinyship`）是本方案的结构参考，不是代码来源。它的 monorepo 把「应用薄、领域厚、配置集中」做通了；它在 Cloudflare 上的实际路径也暴露了不该带进新仓库的成本。

| 题目     | TinyShip 的做法                                                                                | 本仓库的做法                                                                                                                                                                        |
| -------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 仓库形态 | pnpm workspace + Turborepo。`apps/*` 是工作区包，`libs/*` 用 tsconfig 路径引用，不进 workspace | 同样用 pnpm workspace + Turborepo。共享代码一律做成 workspace 包，用 `workspace:*` 依赖。不再使用「路径别名指向源码、包管理器看不见」的 `libs`                                      |
| 应用数量 | Next、Nuxt、TanStack Start 三套对齐，外加文档站                                                | 本期两个应用：`web`、`saas`。不维持框架对齐                                                                                                                                         |
| 渲染     | TanStack Start 在 Workers 上做 SSR，作为 Cloudflare 路径                                       | 内容站和 SaaS 公开页用 Astro 在构建时生成 HTML。SaaS 应用壳用 Vite SPA。Worker 只存在于 `saas`，只处理 `/api/*` 和应用壳的深链回退。不把 TanStack Start、Nitro、vinext 放进默认路径 |
| 数据     | Drizzle，同时维护 PostgreSQL 与 SQLite/D1                                                      | 只维护 D1 一套方言。Drizzle 的 sqlite 方言生成 SQL，Wrangler 迁移目录是唯一应用入口                                                                                                 |
| 事务     | D1 绑定拒绝 Drizzle 的 `BEGIN` / `SAVEPOINT`，TinyShip 用 `runD1Batch()`                       | 从第一天就只用 `DB.batch()`。共享包不提供 `db.transaction()` 给业务代码                                                                                                             |
| 绑定     | `cloudflare:workers` 的 `env`，并要避开已删除的 vinxi                                          | Hono 的 `c.env`。类型来自 `wrangler types`，不手写一份平行的 `Env`                                                                                                                  |
| 领域能力 | 认证、支付、邮件、短信、积分、权限、AI 一开始就在仓库里                                        | 这些都是后续插件。本期仓库里只有插件类型和一个空的注册数组                                                                                                                          |
| 配置     | 根上的 `config.ts` 聚合全部服务                                                                | 每个应用自己的 `app.config.ts`。插件读取自己的配置切片，不在根上做总开关文件                                                                                                        |
| 上传     | Workers 上只允许 R2 binding；Node 上还有 OSS、S3、COS                                          | 本期 SaaS 不接文件。存储插件到来时只走私有 R2 binding，不把云厂商 SDK 打进 Worker                                                                                                   |

TinyShip 的 `apps/tanstack-app/CF-NOTES.md` 记录了 SSR 依赖扫描失败、重复 React、`require`、原生模块和 D1 事务这些问题。本方案用「静态 HTML + SPA + 一个 Hono Worker」避开这条路径，而不是在新仓库里再修一遍。

## 3. 技术栈

选型按规范第 1 节的六问做。没有写出的产品，就是本期不引入。

### 3.1 六问的答案

1. **公开页面能否在发布时生成？**  
   `web` 是内容站。页面在发布时生成，用 Astro 静态输出，未知路径是真实 404。简单工具也是一张预渲染的页面，交互只发生在浏览器里。  
   `saas` 的首页、定价页要求索引，用 Astro 静态生成。仪表盘是登录后工具，用挂在 `/app` 下的 Vite SPA。
2. **为什么不能全部预渲染？**  
   `saas` 要有请求时读取的 API。HTML 壳仍然在构建时生成。不因为「团队熟悉 Next」而上 SSR。
3. **是否使用 Next.js？** 不使用。两个模板都不需要 Next 的能力。
4. **数据用哪一种？**  
   `web` 无服务端数据。  
   `saas` 用一个 D1，作为以后租户行、会话和账本的权威库。本期没有「少了它需求就不成立」的文件、公开配置、队列或实时协调，所以不接 R2、KV、Queues、Workflows、Durable Objects。
5. **异步到哪一层？** 本期请求内完成。失败让调用方重试即可。
6. **是否已有必须保留的外部系统？** 没有。支付、邮件、外部 IdP 留给对应插件，并按规范第 3 节走例外。

### 3.2 锁定的技术

版本在脚手架当天写入锁文件。下表给的是产品代际。开工时如果某一项已有更新的稳定主版本，用更新的那一版，并在选型单里记下实际版本。本期实际锁定：Node.js 22、pnpm 10.33.0、Vite 8.3.8、Wrangler 4.162.0、React 19.3.1、Tailwind CSS 4.3.5、TypeScript 5.9.3、Astro 7.4.12、Vitest 4.1.12、`@cloudflare/vitest-plugin` 1.8.2。TypeScript 不用 7.0.2，因为 typescript-eslint 8.72.2 要求 `typescript < 6.1`。Vitest 不用 5，因为 Workers 测试插件要求 `vitest ^4.1.0`。

| 层             | 选择                                                                                    | 原因                                                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 运行时与包管理 | Node.js 22 LTS，pnpm workspace，Turborepo 2                                             | Node 只负责安装和构建。Worker 内不把文件系统当数据盘。Turborepo 负责按包编排 `typecheck`、`test`、`build`                                 |
| 语言           | TypeScript strict，ESM，`jsx: react-jsx`                                                | 与 Workers、Vite、Astro 的原生模块方式一致                                                                                                |
| 静态页面       | Astro 7，`output: 'static'`                                                             | `apps/web` 整站，以及 `apps/saas` 的公开页。每个公开 URL 一份 HTML。不使用 Cloudflare adapter。`web` 上的简单工具只在该页挂一段浏览器脚本 |
| SaaS 应用壳    | 另一份 Vite + React + TanStack Router，`base` 为 `/app/`                                | 与公开页分开构建，避免 SPA 的软 404 落到营销 URL 上                                                                                       |
| API            | Hono 4                                                                                  | 跑在 Worker 里，路由和中间件足够，依赖面小                                                                                                |
| 校验           | Zod 4                                                                                   | 与 TinyShip 同一主版本。API 入参和 `app.config.ts` 都用它                                                                                 |
| 数据库         | D1 + Drizzle ORM（sqlite 方言）+ Wrangler migrations                                    | 类型在 Drizzle schema，已应用的 SQL 文件只追加、不修改。查询用预编译语句                                                                  |
| UI             | Tailwind CSS 4，shadcn/ui 的组件拷进 `packages/ui`                                      | 组件属于仓库，不在运行时依赖 shadcn 注册表。Astro 页只用设计令牌，不引入 React                                                            |
| 测试           | Vitest；Worker 行为用 `@cloudflare/vitest-plugin`                                       | 纯函数走默认池。碰到绑定的测试跑在 workerd 里。`@cloudflare/vitest-pool-workers` 已改名为这个包                                           |
| 质量           | ESLint（flat config）、Prettier、`wrangler types` 过期检查、`wrangler deploy --dry-run` | CI 在不可信 PR 上做到构建和干跑，不持有生产令牌                                                                                           |
| 部署           | Wrangler 4，`wrangler.jsonc`                                                            | 配置即代码。`compatibility_date` 用开工当日                                                                                               |

React 是 SaaS 应用壳的界面语言。规范把 React 和 Vue 视为打平，本仓库的应用壳选择 React，因为共享组件可以只有一套，也和 TinyShip 的 `libs/ui`、`libs/react-shared` 同一侧。`apps/web` 和 SaaS 公开页不加载 React。Vue 模板不在本期计划里。

### 3.3 本期明确不进入依赖树的东西

Next.js、vinext、OpenNext、Nuxt、TanStack Start、Nitro、Better Auth、Stripe 及其他支付 SDK、邮件 SDK、Drizzle 的 PostgreSQL 驱动、`better-sqlite3`、`pg`、AWS SDK。认证插件以后如果选用 Better Auth，再把它加进该插件的依赖，并确认 Worker 打包结果里没有 Node 原生模块。

## 5. 详细设计

### 5.1 工具链约定

根 `package.json` 是 `private`，`packageManager` 固定 pnpm 版本，`engines.node` 为 `>=22.12.0`。脚本只做转发：

| 脚本             | 行为                                           |
| ---------------- | ---------------------------------------------- |
| `pnpm dev:web`   | 只启动 `apps/web` 的 Astro                     |
| `pnpm dev:saas`  | 同时启动 SaaS 的 Astro、Vite 和 `wrangler dev` |
| `pnpm build`     | Turborepo 构建两个应用                         |
| `pnpm typecheck` | 各包 `tsc --noEmit`                            |
| `pnpm test`      | 各包 Vitest                                    |
| `pnpm cf:types`  | 在 `apps/saas` 运行 `wrangler types`           |
| `pnpm cf:check`  | 两个应用分别 `wrangler deploy --dry-run`       |

Turborepo 的 `build` 依赖上游包的 `build`。`dev` 不缓存。共享包如果只导出 TypeScript 源码，用 `exports` 指向源文件，由应用的 Vite 或 Wrangler 打包，不为每个共享包单独产出 `dist`。`packages/ui` 的 CSS 同样以源文件导出。

ESLint 与 Prettier 放在根上，各包不复制配置。导入排序和未使用变量作为错误。Worker 源码禁止 `any`、禁止 `require`、禁止从 `worker-kit` 以外的地方直接 `new Response` 来返回 API 错误（页面回退除外）。

`.gitignore` 排除 `node_modules/`、`dist/`、`.wrangler/`、`.astro/`、`.dev.vars*`、`.env*`。可以提交的变量模板是各应用里的 `.dev.vars.example`，本期 SaaS 没有密钥，该文件可以只有注释。

### 5.2 共享包

**`@ship/tsconfig`** 提供三份配置：`base.json`（strict、`noUncheckedIndexedAccess`、`moduleResolution: Bundler`）、`react.json`（加上 DOM）、`worker.json`（lib 为 ES2022，types 留空，由应用把自己的 `worker-configuration.d.ts` 加进 `include`）。各包用相对路径 `extends` 到这些文件。`node_modules` 在 gitignore 里，编辑器按包名解析 `extends` 时看不到那一层。

**`@ship/ui`** 放设计令牌和 React 组件。

- `styles/tokens.css` 定义颜色、圆角、字体。`web` 和 `saas` 的 Astro 页，以及 SaaS 的应用壳，都引用它。
- `styles/app.css` 是 Tailwind 入口，只给 SaaS 应用壳用。React 的 peer 依赖是可选的，内容站只引用令牌，不安装 React。
- 组件按 shadcn 的方式以源码存放：`Button`、`Card`、`Input`、`EmptyState`。本期页面够用即可，不预先搬完整组件库。
- 包的 `peerDependencies` 是 `react` 和 `react-dom`。包内不出现 `hono`、`drizzle-orm`、`cloudflare:workers`。

**`@ship/worker-kit`** 只在 Worker 里使用。它导出：

- `createApp()`：创建一个 `Hono<{ Bindings: AppEnv }>`，并挂上 `/api/*` 中间件。中间件在 `next()` 之后写 `Cache-Control: private, no-store` 和 `X-Content-Type-Options: nosniff`。
- `apiError(code, status)`：响应体固定为 `{ "error": "<稳定代码>" }`。不写堆栈、SQL 和内部路径。
- `requestLogger()`：用 `JSON.stringify` 打一条结构化日志，字段包括环境、路由、状态、耗时。失败用 `console.error`。不记录查询串里的令牌、Cookie 和正文。

`AppEnv` 是泛型。`apps/saas` 用生成的绑定类型填上它。`worker-kit` 不依赖某一个应用的 `wrangler.jsonc`。

**`@ship/plugin-sdk`** 只有类型和两个纯函数，见第 5.7 节。

### 5.3 内容站 `apps/web`

这是一个纯静态内容站。页面在构建时生成，公开 URL 可以被索引。可以有简单工具页：交互发生在浏览器里，不保存数据，不需要账号。需要登录、支付、服务端数据或跨页面状态的工具，放到 `apps/saas`，不把这个站升级成单页应用。

页面文案使用英文，方便以后整段搬进国际化插件。本期页面：

| URL              | 文件                            | 要求                                                                   |
| ---------------- | ------------------------------- | ---------------------------------------------------------------------- |
| `/`              | `src/pages/index.astro`         | 标题、description、canonical、可抓取的正文，以及指向指南和工具页的链接 |
| `/guide`         | `src/pages/guide.astro`         | 一篇短文，说明内容页和简单工具的边界                                   |
| `/tools/counter` | `src/pages/tools/counter.astro` | 一个计数器。HTML 里已经有初始数字。按钮只改当前页的数字，不发请求      |
| `/404`           | `src/pages/404.astro`           | 真实 404 页面                                                          |

`robots.txt` 允许收录。`sitemap.xml` 列出 `/`、`/guide`、`/tools/counter`。站名和 canonical 源在 `src/site.ts`。

**构建。** Astro `output: 'static'`，产物在 `dist/`。不使用 Cloudflare adapter。日常开发用 Astro 开发服务器，端口 4322。`pnpm --filter @ship/web preview` 先构建，再用 Wrangler 按生产的资产规则在 4173 预览。验收以 Wrangler 这条路径为准。

**Wrangler。** 没有 `main`。配置只声明资产目录、真实 404 和可观测性：

```jsonc
{
  "$schema": "../../node_modules/wrangler/config-schema.json",
  "name": "ship-web",
  "compatibility_date": "<开工当日>",
  "workers_dev": false,
  "observability": {
    "enabled": true,
    "logs": { "enabled": true, "head_sampling_rate": 1 },
    "traces": { "enabled": true, "head_sampling_rate": 1 },
  },
  "assets": {
    "directory": "./dist",
    "not_found_handling": "404-page",
    "html_handling": "drop-trailing-slash",
  },
}
```

`html_handling` 让 `/guide` 直接得到该页 HTML，而不是先跳到带斜杠的地址。没有 `main` 时，平台仍然会为静态资源准备一个 Worker。日志采样在模板里用 1，因为本地和演示流量极小。接到真实域名、流量上来之后，按规范第 4.1 节把 traces 调回起点再估算账单。

`env.staging` 与 `env.production` 各自重复资产配置，并写自己的 Custom Domain，不继承顶层的本地占位。模板里的主机名使用 `staging.example.com` 和 `www.example.com` 这种明显的占位，并在 README 写明替换条件：目标账户里已有 zone、证书和 DNS。

**样式。** 页面引用 `@ship/ui` 的设计令牌，站点样式写在 `src/styles/site.css`。不引入 Tailwind，不引入 React。

**不包含。** API、D1、R2、KV、Cookie、登录态、环境密钥、路由库、SPA 回退。未知路径的状态码是 404，响应体是 404 页面。浏览器代码里不出现绑定名称。

### 5.4 SaaS 模板 `apps/saas`

一个包，一次构建，一个 Worker。目录分成 `site`、`app`、`worker`，是为了让三种产物边界清楚，不是三个部署单元。

#### 公开页面

Astro 使用 `output: 'static'`，构建到 `apps/saas/dist`。本期页面：

| URL        | 文件                           | 要求                                                                |
| ---------- | ------------------------------ | ------------------------------------------------------------------- |
| `/`        | `site/src/pages/index.astro`   | 标题、description、canonical、可抓取的正文和指向定价页的链接        |
| `/pricing` | `site/src/pages/pricing.astro` | 静态展示 `app.config.ts` 里的方案名称和价格文案。没有结账按钮的后端 |
| `/404`     | Astro 默认 404                 | 真实 404 页面                                                       |

这些页面不读取 D1，不设置 Cookie。`robots.txt` 允许收录，并指向以后会加的 sitemap 的位置；本期可以放一个只包含 `/` 和 `/pricing` 的静态 `sitemap.xml`。

#### 应用壳

Vite 的 `base` 是 `/app/`，`outDir` 是 `dist/app`，`emptyOutDir` 只清空 `dist/app`。入口路由：

| URL             | 作用                                 |
| --------------- | ------------------------------------ |
| `/app`          | 应用首页，说明认证插件启用前没有会话 |
| `/app/settings` | 空状态，演示深链                     |

构建顺序固定为：先 Astro（清空 `dist`），再 Vite（只清空 `dist/app`）。`scripts/build.mjs` 执行这两步，任一失败则中止。`package.json` 的 `build` 只调用这个脚本。

#### Worker

`wrangler.jsonc` 的 `main` 是 `worker/index.ts`。资产配置：

```jsonc
"assets": {
  "directory": "./dist",
  "binding": "ASSETS",
  "not_found_handling": "404-page",
  "run_worker_first": ["/api/*", "/app", "/app/*"]
}
```

含义：

- `/` 和 `/pricing` 由资产层直接返回，不执行 Worker，不计 Worker 请求费。
- 不存在的公开路径返回真实 404，而不是入口 HTML。
- `/api/*` 一定进入 Worker。
- `/app` 与 `/app/*` 进入 Worker。Worker 先用 `ASSETS.fetch` 找对应文件（带哈希的 JS、CSS 会命中）；未命中时返回 `dist/app/index.html`，由 TanStack Router 接过路径。这一步是应用壳的深链回退，范围只限 `/app`。

API 本期只有两个只读路由：

| 方法与路径        | 行为                                                  |
| ----------------- | ----------------------------------------------------- |
| `GET /api/health` | `200` 与 `{ "ok": true }`。不访问 D1                  |
| `GET /api/meta`   | 读取 D1 的 `app_meta`，返回应用名和已启用插件 id 列表 |

任何其他方法，以及任何会改变状态的路径，返回 `405` 或 `404`，错误体使用 `apiError`。不提供匿名写入。规范第 8 节的教材明确这种写入不能开放；本模板从一开始就不放这条路由。

`/api/meta` 的插件列表来自 `worker/plugins.ts` 的数组，不来自数据库里可被请求改写的字段。数据库只保存 schema 版本，用来证明迁移和读取路径是通的。

直接 `return new Response(asset.body)` 时，Hono 中间件不一定能补头。资产响应保持资产层自己的缓存头。API 响应一律走 `c.json`，让中间件写上 `private, no-store`。

三个进程一起开，端口固定：

| Vite dev       | 5174 | 改应用壳，把 `/api` 代理到 8787 |

#### 数据和迁移

D1 绑定名是 `DB`。本地、staging、production 使用三个不同的库名和 ID。本地使用全零 UUID，不创建云端资源。staging 与 production 的 UUID 在配置里留空字符串占位，部署文档要求换成 `wrangler d1 create` 的输出。顶层配置是本地，环境块完整重写 `d1_databases` 和 `assets`，避免把本地占位部署出去。

Drizzle schema 本期只有一张表：

```text
app_meta
  key    TEXT PRIMARY KEY
  value  TEXT NOT NULL
```

迁移 `migrations/0001_app_meta.sql` 创建该表，并插入一行 `schema_version`。文件一旦提交并被应用，以后只追加新文件。

`db/client.ts` 导出 `createDb(d1)` 和 `batch(db, statements)`。业务代码需要多条语句一起成功时调用 `batch`，它底层是 D1 的 `batch()`。包内不重新导出 Drizzle 的 `transaction`。

`GET /api/meta` 使用 `prepare(...).bind(...)`。表名和排序不来自请求。

#### 租户

本期没有租户行，因为还没有会话，无法从会话取得 `tenant_id`。schema 不预留一个可空的 `tenant_id` 列。认证插件增加业务表时，每张表从第一版就带上 `NOT NULL` 的 `tenant_id`，唯一约束写成 `(tenant_id, business_key)`。这个约定写在插件 SDK 的注释和 `plugins/README.md` 里，避免以后出现「先做单租户、再补列」的迁移。

#### 可观测性

与 `web` 相同，模板默认打开 logs 和 traces，采样率为 1，并在部署说明里要求生产按流量改 traces 采样。`compatibility_date` 使用开工当日，不额外手写 `nodejs_compat`。

### 5.5 路由一览

```text
apps/web
  浏览器 → Workers Static Assets
           / 、/guide 、/tools/counter → 对应 HTML
           未知路径 → 404.html，状态码 404

apps/saas
  浏览器 → / 、/pricing、带哈希的静态文件 → 资产层，真实 404
         → /app、/app/*                   → Worker → 文件或 /app/index.html
         → /api/*                          → Worker → Hono
                                              └─ D1.app_meta
```

不开启 Workers Cache。两个模板都没有「公开、可共享、重复读取、值得把免费静态请求改成按请求计费」的动态响应。

### 5.6 配置与环境

`apps/saas/app.config.ts` 用 Zod 解析后导出。本期字段：

- `app.name`
- `app.url`（本地默认 `http://localhost:8787`）
- `pricing`：两个静态方案的名称和展示价格，仅供定价页渲染

秘密不进这个文件。本期没有秘密。以后的插件把密钥放进对应环境的 Worker Secrets，名称写在插件说明里，值放在 `.dev.vars`（已被 gitignore）。

Wrangler 的 `vars` 只放可以公开的值，例如 `APP_ENV=development|staging|production`。环境块不从顶层继承绑定，每个环境写全。

`apps/web` 没有服务端配置。站名、说明和 canonical 源写在 `src/site.ts`。本地预览地址是 `http://127.0.0.1:4173`。换成真实域名时改这一处。

### 5.7 插件契约

本期实现类型、注册点和检查函数。不实现认证、支付、国际化，也不做「扫描目录自动加载」。Worker 的依赖必须在构建时静态可见。

```ts
export interface ShipPlugin {
  id: string;
  version: string;
  /** 该插件拥有的 Drizzle 表。应用的 schema.ts 显式展开。 */
  tables?: Record<string, unknown>;
  /** 挂到 Hono 上的函数。应用在 createApp() 之后逐个调用。 */
  mount?: (app: Hono) => void;
  /** 插件声明必须存在的绑定名。缺失时 checkBindings 失败。 */
  requiredBindings?: readonly string[];
  /** SPA 路由模块的包内导出路径，供应用壳静态导入。 */
  clientRoutes?: string;
}
```

`apps/saas/worker/plugins.ts`：

```ts
import type { ShipPlugin } from '@ship/plugin-sdk';

export const plugins = [] as const satisfies readonly ShipPlugin[];
```

启用一个插件时要同时做四件事，缺一则代码评审不通过：

1. 把该包加进 `plugins` 数组（静态 import）。
2. 把它的表展开进 `db/schema.ts`，生成新的迁移文件并提交。
3. 在 `wrangler.jsonc` 补上它声明的绑定，本地与每个环境都写。
4. 如果它有界面，在应用壳的路由里静态导入 `clientRoutes`。

`@ship/plugin-sdk` 的 `checkBindings(plugins, env)` 在 Worker 启动处理第一次请求时运行一次（模块级只存布尔值，不存请求数据）。缺绑定则 `/api/*` 返回 `500` 和 `{ "error": "plugin_binding_missing" }`，并打结构化日志。这样配置错误会在预览里失败，而不是在某个深路径上才暴露。

插件的迁移编号由应用统一分配。插件包里可以放 SQL 草案供人阅读，Wrangler 只读取 `apps/saas/migrations`。不在运行时拼接迁移。

以后插件的推荐顺序：

| 顺序 | 插件 id   | 加入的能力                                          | 仍要遵守的约束                                                                                                                                                                                                                                                         |
| ---- | --------- | --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | `auth`    | 注册、登录、登出、会话                              | 权威会话在 D1，每次请求读 D1。Cookie 使用 `Secure`、`HttpOnly`、`SameSite` 和可用的 `__Host-` 前缀。变更状态的请求校验 Origin。实现优先评估 Better Auth 的 D1 适配，并在 Workers Paid 上测量口令哈希的 CPU；测不进预算就改通行密钥。Free 的 10 毫秒 CPU 不用于口令哈希 |
| 2    | `i18n`    | `/en/`、`/zh/` 这样的可分享 URL，文案目录，hreflang | 不按 IP、Cookie 或浏览器语言改写爬虫请求。公开页的各语言版本在构建时生成                                                                                                                                                                                               |
| 3    | `billing` | 托管支付页、webhook、D1 账本                        | 按规范第 3 节登记外部支付机构。Worker 不接触卡数据。webhook 校验签名和事件 ID，用 `Idempotency-Key` 落账。前端回跳不算支付成功                                                                                                                                         |
| 4    | `storage` | 私有 R2、短时预签名上传                             | 绑定不能签发预签名，在 Worker 内签名。有效期用分钟到小时。桶保持私有。对象键以 `tenants/{tenantId}/` 开头，租户来自会话                                                                                                                                                |
| 5    | `email`   | 事务邮件                                            | 发送失败可重试时再引入 Queues。在此之前不把队列加进模板                                                                                                                                                                                                                |

每个插件到开工时另写一节设计，并填写规范第 16 节。本文件不替代那一节。

`auth` 插件替换「默认拒绝写请求」的方式是导出一个 `requirePrincipal()`。未启用 `auth` 时，`worker-kit` 的写路由助手直接返回 `401` 和 `{ "error": "auth_required" }`。因此后续即使有人在核心包加了 `POST`，默认也不可匿名调用。

### 5.9 CI

GitHub Actions 在 push 和 pull request 上执行：

```text
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
pnpm cf:check
```

`cf:check` 只做 dry-run，不登录生产账户。工作流不设置 `CLOUDFLARE_API_TOKEN`。远程迁移和 `wrangler deploy` 留在有审批的发布流程，不进这条流水线。

生成类型的检查：CI 再跑一次 `wrangler types`，然后 `git diff --exit-code -- apps/saas/worker-configuration.d.ts`。有差异就失败，提示开发者提交新类型。

### 5.10 部署说明要写进各应用 README 的步骤

每个应用一份短 README，只保留该应用的命令。共同顺序：

1. 安装依赖，复制并按需修改占位域名。
2. `pnpm typecheck && pnpm test && pnpm build`。
3. 内容站：`wrangler dev` 看资产，然后按环境 `deploy --dry-run` 再 `deploy`。
4. SaaS：先对目标环境 `wrangler d1 migrations list`，再 `migrations apply`，再 dry-run，再 deploy。生产库的 `--remote` 需要单独批准。
5. 核对账户、环境名、D1 UUID 和主机名。

模板的 README 不复制规范全文，用链接指向第 12 节和第 15 节。

## 8. 实施顺序

按这个顺序提交，每一步都可以单独运行检查：

1. **仓库骨架。** pnpm、Turborepo、TypeScript、ESLint、Prettier、gitignore、CI 空跑。共享 tsconfig。
2. **`packages/ui`。** 令牌、Tailwind 入口、按钮和空状态。
3. **`apps/web`。** Astro 静态页、一个简单工具页、Wrangler 纯资产配置（真实 404）、README、选型单。跑通 dev、build、dry-run，并在 Wrangler 预览里确认深链和 404。
4. **`packages/worker-kit` 与 `packages/plugin-sdk`。** 含单元测试。
5. **`apps/saas` 的公开页和构建脚本。** 先只有 Astro 和空 Worker 的健康检查，打通「静态优先、API 走 Worker」。
6. **D1。** schema、迁移、`/api/meta`、workerd 测试、三个环境的配置占位。
7. **应用壳。** `/app` 构建进 `dist/app`，Worker 做该前缀的回退。预览里核对 200、404 和深链。
8. **文档收尾。** 两个 README、两份选型单、`plugins/README.md` 里的启用步骤。

第 3 步结束就可以部署内容站模板。第 7 步结束才算 SaaS 模板可用。不要在第 5 步之前把仪表盘和 API 缠在一个 Vite 中间件里，否则验收路径会变成 Node 开发服务器，而不是 workerd。
