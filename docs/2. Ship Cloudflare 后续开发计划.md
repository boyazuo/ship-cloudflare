# Ship Cloudflare 后续开发计划

**文档版本：** 1.1  
**日期：** 2026-11-15  
**地位：** 骨架交付之后的开发顺序。平台限额、一致性和安全以 [技术选型与开发规范](./0.%20Cloudflare%20技术选型与开发规范.md) 为准。目录、构建和插件契约以 [技术方案](./1.%20Ship%20Cloudflare%20技术方案.md) 为准。本文决定接下来做哪些模块、插件和页面。  
**相对 1.0：** `auth` 只做用户认证。不建 `tenant`、`membership`，业务表不预留 `tenant_id`。隔离键是会话里的 `user_id`。  
**相对技术方案 5.7：** 五个插件 id 保留。实施顺序改成：先补法律页，再做 `auth`、`billing`、`email`、`storage`，`i18n` 等到第二种语言成为明确需求。组织、用量和操作员入口另有触发条件，不排进默认阶段。

阅读顺序：第 1–3 节是缺口；第 4 节是可以开工的阶段；第 5–6 节是先不做的东西。

---

## 1. 骨架里已经有的

两个应用可以独立部署。插件数组是空的，写请求返回 `auth_required`。

| 位置 | 已有 | 克隆之后仍然缺 |
| --- | --- | --- |
| `apps/web` | `/`、`/guide`、`/tools/counter`、`/privacy`、`/terms`、真实 404、sitemap | — |
| `apps/saas` 公开页 | `/`、`/pricing`、`/privacy`、`/terms`、真实 404、sitemap。价格来自 `app.config.ts`，没有结账。隐私页只写 `app_meta` | 定价页还没有结账入口 |
| `apps/saas` 应用壳 | `/app` 只读 `/api/meta`，`/app/settings` 是空状态 | 登录、会话、账户设置 |
| API | `GET /api/health`、`GET /api/meta`。其他写方法由 `rejectUnauthenticatedWrite` 拒绝 | 主体、账本、对象存储 |
| 数据 | 一张 `app_meta`。还没有用户表 | 用户和会话 |
| `@ship/ui` | `Button`、`EmptyState` | 登录和设置要用的 `Input`、`Label` |
| `@ship/plugin-sdk` | 类型、`checkBindings`、静态注册 | 真实插件包 |
| 绑定 | SaaS 一个 D1。内容站没有 Worker 脚本 | 认证会加限流和 Turnstile；存储才会加 R2 |

内容站继续只放构建时生成的页面，以及不保存数据的浏览器工具。要账号、支付或服务端数据的功能进 `apps/saas`。

## 2. 取舍

克隆这份模板的人，下一步是一个已登录的单用户产品：一个 Worker、一个 D1，业务行上的 `user_id` 来自会话，文件到来时再加一个私有 R2。规范第 6.4 节的多租户不进 `auth`。需要第二个成员时再做 `orgs`，那时才引入 `tenant_id`。

一项工作进入默认阶段，要满足下面三条里的一条：

1. 没有它，第一个需要登录或收款的产品做不下去。
2. 规范第 10 节要求公开上线前就具备：可撤销的会话、对象级授权、账户恢复、删除、导出，以及匿名写入的服务端校验。
3. 它是上述单用户产品里的一块，并且一个插件加一个页面就能把约定示范完。

TinyShip 用来对照能力，不搬它的代码，也不搬它的多供应商矩阵。每个插件先接一个实现。第二个供应商要有第二个真实调用方再加。

| TinyShip 里的库 | 本仓库的处理 |
| --- | --- |
| `auth` | 阶段 1 插件。先评估 Better Auth 的 D1 适配和口令哈希 CPU |
| `payment` | 阶段 2 的 `billing`。托管支付页，Worker 不接触卡数据 |
| `email` | 阶段 3。先做事务邮件 |
| `storage` | 阶段 4。只走私有 R2 binding |
| `i18n` | 阶段 5，等第二种语言确定之后 |
| `permissions` | 不进 `auth`。认证只识别当前用户。第二种角色出现再拆插件 |
| `credits` | 有按量计费的产品再做，账本在 D1 |
| `pricing` | 已经在 `app.config.ts`。结账状态以 D1 账本为准 |
| `seo` | 公开页已经有标题、canonical、sitemap。hreflang 放进 `i18n` |
| `validators` | 继续用 Zod，不单独成包 |
| `database` | 继续放在 `apps/saas/db` |
| `sms`、`affiliate`、`ai` | 默认不做，见第 6 节 |

## 3. 建议增加的插件和页面

### 3.1 插件

启用方式不变，仍然是技术方案第 5.7 节的四步：静态导入、展开表并提交迁移、写全绑定、有界面就静态导入 `clientRoutes`。不扫描 `plugins/` 目录。

| 插件 | 阶段 | 绑定 | 它拥有的数据 | 页面 |
| --- | --- | --- | --- | --- |
| `auth` | 1 | 现有 `DB`；登录路由加 Rate Limiting binding；注册加 Turnstile secret | `user`、`session`、`audit_event`。不建租户和成员关系。属于用户的表从第一版就带非空 `user_id` | `/app/sign-in`、`/app/sign-up`、改写后的 `/app` 与 `/app/settings` |
| `billing` | 2 | `DB`；支付密钥用 Worker Secret | 订阅、发票和入账事件。幂等键有唯一约束。金额权威在 D1 | 定价页增加结账链接；`/app/billing` |
| `email` | 3 | 发信密钥。队列等到发送失败必须离开本次请求再重试时再加 | 投递记录、抑制名单。正文模板放在插件包内 | 无独立页面。收据和账户邮件由调用方触发 |
| `storage` | 4 | 一个私有 R2。本地、staging、production 各写各的桶 | 对象键、所有者和校验信息在 D1。对象键以 `users/{userId}/` 开头 | `/app/files`，只做上传和列出自己的对象 |
| `i18n` | 5 | 无 | 文案目录随包发布。公开页在构建时生成 `/en/`、`/zh/` | 内容站和 SaaS 公开页各一份语言版本 |

`auth` 替换写保护的方式已经留好了：它导出 `requirePrincipal()`，未启用时 `worker-kit` 继续返回 `401` 和 `{ "error": "auth_required" }`。用户 id 从这次校验的会话读取。调用方提交的 `user_id` 不参与授权。

注册时在同一次 `batch()` 里创建用户。不创建个人租户，也不创建成员关系。

### 3.2 页面

公开页用 Astro 在构建时生成，文案用英文，和现有页面一致。应用壳页面挂在 `/app`，不进 sitemap。

| URL | 应用 | 阶段 | 作用 |
| --- | --- | --- | --- |
| `/privacy`、`/terms` | `web` 和 `saas` 各一份 | 0 | 可抓取的法律页，并写入各自的 sitemap。阶段 1 收集邮箱时，同一改动里改写 SaaS 这份隐私页，写明实际字段、保留期和删除方式 |
| `/app/sign-in`、`/app/sign-up` | SaaS 应用壳 | 1 | 注册和登录。匿名提交由 Turnstile 的服务端校验挡住 |
| `/app` | SaaS 应用壳 | 1 | 显示当前用户。未登录时链到登录页 |
| `/app/settings` | SaaS 应用壳 | 1 | 资料、会话列表、导出、删除账户。删除同时作废会话 |
| `/pricing` | SaaS 公开页 | 2 | 保留静态价格。方案上的按钮指向托管支付页 |
| `/app/billing` | SaaS 应用壳 | 2 | 显示 D1 里的订阅状态。支付机构跳回本站只刷新状态，不授予权益 |
| `/app/files` | SaaS 应用壳 | 4 | 申请短时预签名、上传、列出当前用户的对象 |
| `/en/…`、`/zh/…` | `web` 与 SaaS 公开页 | 5 | 可分享的语言 URL、hreflang、self-canonical |

账户恢复页是否存在，由 `auth` 的设计说明决定。通行密钥可以在设置页里登记第二把钥匙。邮件找回则使用 `/app/reset`，并且阶段 1 就要有一封事务邮件。

应用壳导航在启用对应插件时手写链接。`ShipPlugin` 不加导航注册表。

### 3.3 随插件一起补的共享代码

这些改动放进当时那个阶段，不提前做框架。

| 改动 | 落点 | 阶段 |
| --- | --- | --- |
| `Input`、`Label` | `packages/ui` | 1。登录和设置要用。不搬一套完整组件库 |
| `requirePrincipal()` | `plugins/auth` | 1 |
| 幂等键读取 | `packages/worker-kit` 一个函数 | 2。产生外部副作用的 POST 使用调用方提供的 `Idempotency-Key` |
| 结构化日志里的请求 id | `packages/worker-kit` | 1。沿用现有字段，补请求 id。不记录 Cookie、令牌和正文 |

文件列表第一版用固定上限。出现翻页需求时再加规范第 4.3 节的游标。`shortcut: 固定上限，列表会超过这一页时再改游标。`

## 4. 阶段

每个插件开工前先写 `plugins/<id>/DESIGN.md`。绑定、数据类别或外部依赖有变化时，更新 `apps/saas/SELECTION.md` 里对应行。内容站不因为 SaaS 插件增加 Worker、D1 或密钥。

### 阶段 0：法律页

不依赖设计说明，也不新增绑定。

- `apps/web` 与 `apps/saas` 各增加 `/privacy`、`/terms`，写入 sitemap。
- 页面说明当前站点保存什么。这一阶段 SaaS 只有 `app_meta`，不写尚不存在的账户字段。

完成时：四个 URL 都是 200，源码里有正文；未知路径仍是 404。

### 阶段 1：`auth`

设计说明先关闭三件事，再写迁移：

1. Better Auth 的 D1 适配能否进 Worker 包，包里没有 Node 原生模块。
2. 在 Workers Paid 上测量所选口令哈希的 CPU。测不进预算就改通行密钥。Free 的 10 毫秒 CPU 不用于口令哈希。
3. 账户恢复走通行密钥，还是走邮件。走邮件时，本阶段包含一封事务邮件，阶段 3 再把发信收成完整插件。

本阶段包含：

- 注册、登录、登出。会话 id 高熵且不透明，权威记录在 D1，每次请求读 D1。
- Cookie 使用 `Secure`、`HttpOnly`、`SameSite`，能用 `__Host-` 前缀就用。变更状态的请求校验 Origin。
- 只建用户和会话。属于用户的表，唯一约束写成 `(user_id, business_key)`。不建租户表，不预留 `tenant_id`。
- 注册入口的 Turnstile，由 Worker 做 Siteverify，核对 hostname 和 action。
- 登录入口的 Rate Limiting binding。精确的业务配额以后写 D1，不写进这条近似限额。
- 导出与删除。删除账户时作废该用户的会话。
- `audit_event` 记录登录、登出和删除，和对应的业务写入放在同一次 `batch()`。这一阶段没有操作员界面。
- workerd 测试：未登录的写请求被拒绝；错误的 Origin 被拒绝；请求体里的 `user_id` 不能换成另一个用户；删除之后原会话失效。

`/privacy` 在这个阶段改成账户数据的真实说明。

完成时：预览里可以注册并看到 `/app` 上的当前用户，刷新 `/app/settings` 仍是应用壳，`POST` 未登录返回 `auth_required`。内容站的 Wrangler 配置仍然没有 `main`。

### 阶段 2：`billing`

按规范第 3 节登记支付机构。优先用对方的托管支付页。

- Webhook 校验签名、时间窗和事件 id。同一事件重复投递只入账一次。
- 前端跳回 `/app/billing` 只触发读账本。权益以账本里的最终状态为准。
- 定价页的按钮换成托管支付页链接。价格文案仍来自 `app.config.ts`。
- 测试使用支付机构的 sandbox。预览环境不使用生产密钥。

完成时：sandbox 里一笔成功支付和一次重复 webhook 之后，D1 只有一条入账；跳回站内不会凭空变成已付款。

### 阶段 3：`email`

事务邮件：支付收据，以及阶段 1 若还没有做完的账户邮件。验证码、收据和以后的营销邮件分开域名和退订。

先在请求内发送，把投递结果写入 D1。发送失败需要在响应用户之后继续重试时，再给这个插件加 Queues、有限重试和死信队列。在此之前 SaaS 不增加队列绑定。

外部邮件商同样走规范第 3 节的例外。日志不写完整邮件地址和正文。

完成时：一封收据可以在 staging 发出，失败会留下可查询的投递记录，预览不会打到生产发信。

### 阶段 4：`storage`

一个私有桶。浏览器直传使用 Worker 内签名的单对象 URL，有效期按分钟到小时，并绑定 Content-Type。签名材料放在该环境的 Secret。

D1 记下对象键、用户和校验信息。对象写入和数据库写入之间没有共同事务：数据库有记录而对象缺失时，列表接口把该行标成不可用。孤立对象的清扫等真实出现残留再加 Cron。`shortcut: 不做定时清扫，出现残留对象后再加幂等任务。`

`/app/files` 只服务当前会话的用户。列表使用固定上限。

完成时：一个用户上传的对象，另一个用户的会话列不出来，也签不出对方前缀的 URL。桶保持私有。

### 阶段 5：`i18n`

第二种语言已经确定要做，再开工。公开页的英文和中文都在构建时生成。不按 IP、Cookie 或浏览器语言改写爬虫请求。

应用壳的文案在同一阶段抽出来。抽之前壳可以继续只有英文。

完成时：两种语言的首页、定价页和法律页都有互指的 hreflang 和 self-canonical；未知语言前缀是 404。

## 5. 有触发条件再做

下面这些不排进阶段 0–5。触发条件成立时另写设计说明，再决定它是新插件还是某个现有插件里的一组路由。

| 模块 | 触发条件 | 做成什么 |
| --- | --- | --- |
| `orgs` | 一个产品要有第二个成员 | 租户、成员、邀请、`/app/team`。邀请信依赖阶段 3。从这次迁移起，租户数据带非空 `tenant_id`，id 来自会话。在此之前没有租户列 |
| 第二种角色 | 用户之外出现不同权限 | 从 `auth` 拆出对象级权限。在此之前一行数据只属于会话里的用户 |
| `credits` | 产品按用量扣减 | D1 账本和幂等键。Analytics Engine 可以做聚合，金额以 D1 为准 |
| 操作员入口 | 需要在不写 SQL 的情况下封禁用户 | Access 放在入口前，应用内再核对允许名单。界面读 `audit_event`，并在封禁时写审计。Access 不替代这层核对 |
| Queues | 阶段 3 的邮件必须异步重试，或出现规范第 5.6 节的 outbox | 加在需要它的那个插件上，带死信和告警 |
| Workflows | 步骤要跨过分钟或天，并且中间会等待 | 每个有副作用的步骤使用稳定幂等键 |
| Durable Objects | 某个实体要强一致协调，例如不能超卖的名额 | 一个实体一个 ID，ID 含 `userId`。出现租户后再把 `tenantId` 放进 ID |
| KV | 有允许延迟生效的公开配置 | 权威数据仍留在 D1。会话不放 KV |
| 内容后台 | 规范第 9 节的条件成立：多人、草稿、媒体或定时发布，并且 Git 发布的延迟已被拒绝 | 给内容站加 Worker、D1、R2，员工入口用 Access。这是内容站的一次选型变更，不放进 SaaS 模板 |
| 检索或生成 | 规范第 2 节对应行，并且数据区域评审通过 | 单独选型。默认模板不接 Workers AI、Vectorize 或 AI Search |
| Playwright | 阶段 1 的手工预览已经盖不住会话和 Origin | 加少量端到端检查。在此之前继续用预览清单 |
| 拆出单应用的 CLI | 有人必须离开这个 monorepo 交付 | 单独做。两个应用继续各自部署 |

## 6. 继续不做

这些项保持技术方案第 7 节的决定，默认阶段也不打开：

- 第二个前端框架，以及 Next.js、Nuxt、TanStack Start、SSR。
- 运行时扫描插件、为每个租户创建 D1、按租户拆目录。
- Workers Cache、Hyperdrive、Cloudflare for SaaS、Workers for Platforms。客户自带域名或客户自带代码出现时再按规范第 6.4 节立项。
- 短信、联盟、营销邮件、站内通知、功能开关、主题切换、博客引擎、第三个文档应用。
- 把 TinyShip 的业务代码或它的多云存储、多支付供应商抄进来。
- 在 `@ship/ui` 里预先放进当前页面用不到的组件。

## 7. 阶段之间的依赖

```text
阶段 0 法律页
   └─ 阶段 1 auth
        ├─ 阶段 2 billing
        │    └─ 阶段 3 email（收据；邮件找回若在阶段 1 已做，这里扩展）
        └─ 阶段 4 storage
阶段 5 i18n 只依赖公开页文案，不依赖 1–4
orgs 依赖阶段 1，邀请依赖阶段 3
```

阶段 0 可以马上做。阶段 1 从设计说明和 CPU 测量开始。阶段 2 和阶段 4 都依赖会话里的用户，彼此不依赖。阶段 3 依赖阶段 2 的收据；如果账户恢复选择发信，发信的最小部分提前到阶段 1。
